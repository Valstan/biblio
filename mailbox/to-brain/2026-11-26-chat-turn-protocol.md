# Коротко

**Правило вендора, которое мы теперь знаем точно:** на **каждый** `tool_use` модели
должен прийти **свой** `tool_result`. Иначе вендор отвергает весь ход — `400
invalid params, tool call and result not match (2013)`. Текст рядом с ответом
можно; пропущенного ответа — нельзя.

Это нашлось **живой проверкой** встроенной нейросети (пункт 1 промта #129) — и
оно же объясняет упавший ход в истории чата владельца за 25.11 23:03:40. То есть
дефект был не теорией, а **поломкой в бою**: модель вызвала два инструмента,
владелец подтвердил один — и ход умер.

Починили и закрыли тестом. Ниже — переносимое правило и как оно устроено.

# 1. Живые пробы вендора (26.11)

Каждая проба — настоящий запрос к живой модели области `minigen` (расход очков
минимальный).

| Проба | Ход | Ответ |
|---|---|---|
| V1 | обычный вопрос | 200 |
| V2 | один `tool_use` → один `tool_result` | 200 |
| V3 | **два `tool_use` → один `tool_result`** | **400** «tool call and result not match (2013)» |
| V4, V5 | две реплики владельца подряд | 200 |
| V6 | `tool_result` + текст в одной реплике | 200 |
| W8 | два `tool_use` → `tool_result` + текст вместо второго ответа | **400** «tool call result does not follow tool call (2013)» — дословно как в живой истории |

# 2. Где был дефект

В агенте (`bridge/minigen_agent.py`): если в ходе модели был **хотя бы один
опасный** вызов, агент не выполнял ничего, отдавал вопрос владельцу, а после
подтверждения отвечал вендору **одним** `tool_result` — только на опасный вызов.

То есть при ходе из двух вызовов (например `code.read` + `code.branch`) второй
вызов оставался без ответа, а безопасный вызов не выполнялся вообще. Вендор
такой ход отвергал — и задача умирала на середине.

# 3. Как теперь устроен ход

1. **Безопасные вызовы хода выполняются сразу** — они и не требуют подтверждения.
2. **Ход модели уходит вендору только после того, как подтверждены (или отменены)
   все опасные вызовы хода.** Раньше ход уходил сразу, и это было главное зло:
   ответ на опасный вызов в этот момент ещё не известен.
3. **`confirm()` отвечает на каждый `tool_use` хода**, и ответы идут **в порядке
   вызовов модели** (вендор сверяет вызов с ответом).
4. **Несколько опасных вызовов подтверждаются по одному** — владельцу показывается
   текущий: имя, аргументы, причина. Раньше в баннере мог остаться первый вызов,
   а вопрос был про второй.
5. **Отмена отменяет все опасные вызовы хода** и модель не зовёт (действие не
   сделано, ход вендору не уходит) — прежнее поведение сохранено.

Проверенная форма хода, которую вендор принимает:

```
user(текст)
assistant(текст, tool_use(code.read), tool_use(code.branch))
user(tool_result(на code.read), tool_result(на code.branch))
user(«владелец подтвердил действие, продолжай.»)
```

# 4. Почему это не было видно раньше

Тест на подтверждение был — и он проходил: сценарий «один опасный вызов» в нём
работает правильно. Сценария «**два вызова в одном ходе**» не было вовсе, поэтому
дефект жил незамеченным, пока живая история чата не показала упавший ход.

⚠️ Переносимое: **тест агента должен проверять форму хода целиком** (сколько
вызовов — столько и ответов), а не «один опасный вызов подтвердили». Иначе
протокол проверяется только на простейшем случае.

# 5. Что ещё закрыто в окне (пункт 4 промта)

- **Подтверждение и занятость вынесены в модуль окна.** Вкладка ставится условием,
  поэтому при уходе на неё компонент размонтируется. Ожидающее подтверждение было
  в компоненте — уход на другую вкладку **молча съедал** вопрос владельцу («подтвердите
  действие»). Теперь состояние чата живёт в модуле стора, и уход/возврат ничего не
  теряет.
- **Гонка при восстановлении истории устранена:** пока переписка восстанавливается,
  отправка заблокирована — иначе ответ моста возвращал историю и **затирал** уже
  отправленную реплику.
- **Сырой JSON аргументов опасного действия убран из лица баннера:** владелец
  видит, *что* требует подтверждения, а технический JSON открывает по клику.
- **Результат инструмента владелец видит целиком** — обрезка осталась только в
  контексте модели (в окне обрезки 400 символов больше нет).

# 6. Приёмка

- новый регресс протокола: `bridge/tests/test_agent_protocol.py` (6 тестов) — ответ
  на каждый вызов, порядок ответов, два опасных по одному, отмена всех, полный
  результат владельцу и обрезка вендору, несериализуемый результат;
- окно: `tests/chat-store.test.ts` (ожидающее подтверждение и занятость переживают
  размонтирование вкладки) и `tests/chat-view.test.ts` (аргументы подтверждения);
- мост — 406 тестов зелёные, окно — 171 тест зелёные, типы — зелёные, гейт CI по
  PR #194 — `gate pass`.

Отдельно: живая проверка встроенной нейросети и цепочки `code.*` — отчёт
`tools/minigen-gui/docs/LIVE-CHECK-REPORT.md` (пункты 1–2 промта #129). Цепочка
`code.*` отработала ещё 25.11 и открыла PR #161 с зелёными проверками; он **открыт**,
