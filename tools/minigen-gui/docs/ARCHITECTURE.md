# Архитектура «МиниГена» (графическая программа)

Заказ владельца (23.11.2026): «Миниген нужно будет переписать на графический
интерфейс… собрать в одну кучу, сделать одну единую программу с графическим
интерфейсом под Windows». План работ — `docs/plans/minigen-gui-rewrite.md`
в корне репозитория.

## Слои

```
┌───────────────────────────────────────────────────────────────┐
│ Слой 4 — встроенная нейросеть (MiniMax M3 / M3.1-Flash)       │
│ агент-цикл: сообщение → вызов инструмента → наблюдение → ответ │
│ системный промпт = docs/knowledge-pack.md + каталог инструментов│
└───────────────────────┬───────────────────────────────────────┘
                        │ инструменты (тот же реестр, что у кнопок)
┌───────────────────────▼───────────────────────────────────────┐
│ Слой 3 — окно: Electron 43 + TypeScript + React 18            │
│ вкладки: Области · Статистика · Сеть · Чат · Журнал · Гены · Агенты · Настройки│
└───────────────────────┬───────────────────────────────────────┘
                        │ IPC (contextBridge) + JSON-lines поверх stdio
┌───────────────────────▼───────────────────────────────────────┐
│ Слой 2 — мост: Python, bridge/minigen_bridge.py               │
│ команды → ядро; состояние → окно; действия → те же функции    │
└───────────────────────┬───────────────────────────────────────┘
                        │ импорт модулей из C:\Users\valstan\bin
┌───────────────────────▼───────────────────────────────────────┐
│ Слой 1 — ядро (Python, боевой код, НЕ переписывается)         │
│ autheal · netwatch · sessionwatch · minigen_core               │
└───────────────────────────────────────────────────────────────┘
```

**Правило слоёв:** у каждого слоя одна ответственность, логика не
дублируется. То, что уже умеет Python-ядро, GUI не переписывает — GUI
спрашивает и показывает.

## Почему так

| Решение | Причина |
|---|---|
| Ядро осталось на Python | Демоны боевые и несут выученные уроки (грабли `G678`–`G681`). Переписывать их в TypeScript — значит выбросить эти уроки. |
| Мост на JSON-lines | Один процесс, одна схема, легко отлаживать и проверять (`python bridge/minigen_bridge.py` работает и без окна). |
| Electron + TS + React | Тот же стек, что у «Матрицы РМЗ»: владелец его знает, сборка и обновление — теми же руками. |
| Вендор через Anthropic-протокол | Проверено пробой 23.11: `POST {baseURL}/messages`, `Authorization: Bearer <токен области>`. Ключ в `config.yaml` — заглушка; рабочий токен лежит в сторе авторизации области. |
| Опасные действия — через подтверждение | Нейросеть не может сделать то, чего не может сделать владелец через интерфейс. |
| База — общий контейнер, а не таблица на каждую сущность | Версия программы не должна быть условием существования данных: новая возможность = новый вид, а не новая таблица. Иначе база из старой версии перестаёт открываться (промт #92). |
| Выгрузка базы — JSON, а не бинарный SQLite | Файл переживёт смену версии SQLite, читается глазами и годится для переноса между машинами. |

| `src/shared/types.ts` | общий контракт данных окна и моста |

## Потоки данных

**Наблюдение (каждые 5 с):** окно → `state.snapshot` → мост → ядро → снимок
(области, сеть, демоны, статистика) → окно.

**Действие:** кнопка → `minigen:call` → мост → команда → функция ядра →
журнал → ответ в окно.

**Файлы оператора (промт #90):** окно (кнопка или перетаскивание) → **путь**
файла → мост читает файл **у себя** (`bridge/minigen_files.py`) → содержимое
кладётся в ход **блоками** (текст документа / картинка) → уходит вендору.
Окно на диск не ходит: ни при выборе файла, ни при перетаскивании. Мост помнит
список приложенных файлов — нейросеть читает только их (`files.attach`), а
произвольные файлы с диска ей недоступны.

Ридер файлов знает **потолки** (иначе файл-«бомба» вешает мост): размер файла,
размер картинки (в base64 — так её считает вендор), **сторона** картинки, длина
текста, число строк (на всю книгу), **распакованный** объём (zip и PDF) и
**время** чтения. Превышение ⇒ честное сообщение оператору с полным путём
файла, а не зависание. Вид файла определяется по **содержимому** (картинка с
чужим расширением — всё равно картинка), и по содержимому же определяется, что
файл вообще текст.

⚠️ **Картинку вендор принимает не всякую**: протокол `/messages` (Anthropic-совместимый)
берёт только `image/jpeg`, `image/png`, `image/gif` и `image/webp`, а отвергнутый
запрос убивает **весь** ход. Поэтому мост проверяет картинку **до** отправки:
BMP переводит в PNG сам (своим кодом), неподдерживаемый формат и слишком
крупная картинка — честное сообщение оператору, ход продолжается.

**Чат:** реплика → `chat.send` → агент-цикл → модель → вызов инструмента →
мост → ядро → результат обратно модели → ответ владельцу. Опасный
инструмент ⇒ ответ вида `confirm` ⇒ окно спрашивает ⇒ `chat.confirm`.

## Локальная база «МиниГена» (заказ владельца 24.11, промт #92)

У программы есть **своя база**: `%LOCALAPPDATA%\minigen-gui\minigen.db`
(SQLite, рядом с `settings.json`). В ней промты, планы и всё, что «МиниГен»
копит на машине владельца. Путь и содержимое — **только локально**: файл
уходит с машины лишь по явному действию оператора.

### Почему общий контейнер, а не таблицы

```sql
records(id, kind, key, payload, version, created_at, updated_at, deleted_at)
schema_meta(key, value)          -- версия схемы хранилища и служебные отметки
```

- **вид (`kind`)** — что это за данные: `prompt`, `plan`, `prompt-mark`,
  `prompt-dispatch` и будущие;
- **ключ (`key`)** — устойчивый идентификатор записи внутри вида;
- **содержимое (`payload`)** — JSON: форма записи может меняться, не ломая
  контейнер.

Версия программы **не знает** версии базы — она знает, какие `kind` понимает.
Поэтому новая возможность = новый вид или новое поле в `payload`, а **не**
новая таблица. Схема хранилища меняется только вперёд и только добавлением;
база из более новой программы открывается как есть и не понижается.

### Чужое и будущее не выбрасывается

Импорт разбирает файл по видам: известный вид переносится, незнакомый —
**не выбрасывается**, а кладётся в «неразобранное» (`unparsed`): запись
целиком, с пометкой своего вида. Такое «неразобранное» уезжает в следующей
выгрузке, а когда программа заучит этот вид — `promote_unparsed` разложит
записи по местам. Это и есть «структура не привязана к версии».

### Конфликт решает оператор

Если в базе уже есть запись с тем же видом и ключом и содержимое отличается —
программа **не перезаписывает молча**: импорт спрашивает («взять из файла» /
«оставить своё» / «положить рядом»), и без решения запись остаётся нетронутой.

### Выгрузка и импорт

- **выгрузка** — один файл `.minigen.json`: манифест (версия схемы, сколько
  записей каждого вида), все записи и контрольные суммы;
- **импорт** — сначала разбор (`db.inspect`, ничего не меняет), потом решение
  оператора по спорным записям, потом заливка (`db.import`) с отчётом.

### Старая база хранилища

До перехода на универсальную базу промты лежали в `prompts.db` — с таблицей
на каждую сущность (привязка к версии программы). Данные переносятся в новую
базу при каждом старте программы (`migrate_legacy_store`), но переносится
только то, чего в новой базе ещё нет, — перенос безопасный и повторяемый.
**Старый файл остаётся на месте** как запасная копия. Если перенос не прошёл,
хранилище читает старый файл — у владельца промты не исчезают из окна.

## Точки отказа и что происходит

| Что сломалось | Поведение программы |
|---|---|
| Мост не поднялся (нет Python) | В шапке — «мост не запущен», вкладки пустые, кнопки не работают. Сторожа при этом **продолжают работать**: они живут отдельно. |
| Модель недоступна | Чат честно сообщает: «нейросеть недоступна», управление остаётся у сторожей. |
| Токен области протух | Модель недоступна (401). Лечащий обновляет токен — после этого чат снова работает. |
| Конфиг областей читается наполовину | Мост читает его с повтором и пишет **атомарно** (иначе панель и демоны ловят битый JSON — такая ошибка была в журнале 23.11). |
| Конфиг всё же не прочитан | В шапке окна — «конфиг не читается!», список областей пуст, но программа не падает. |

## Чего программа НЕ делает

- Не чинит ничего «на всякий случай»: каждое действие — по команде владельца.
- Не дублирует логику демонов.
- Не раскатывает себя на боевую машину (это отдельное действие и только по
  слову владельца).
- Не ходит в чужие области и репозитории.

## Демоны: кто их держит (Ф6)

Старая веб-панель `127.0.0.1:8099` и страница управления `:8098` архивированы
(код — в `tools/minimax-project-areas/archive/`). Но супервизор панели держал
не только панель, а трёх демонов, поэтому роль процесс-менеджера перешла к
программе:

```
автозапуск Windows (ярлык «МиниГен (демоны)»)
   └─ pythonw bridge/minigen_bridge.py --daemon      ← без окна и без консоли
        └─ поток присмотра: раз в минуту проверяет демонов,
           поднимает упавшего (пауза 20 с перед подъёмом:
           демон мог подняться сам после раскатки кода)
```

| Что | Где |
|---|---|
| определение демонов, поиск процессов, старт/стоп/рестарт | `bridge/minigen_daemons.py` |
| команды `daemons.status/start/stop/restart` | `bridge/minigen_bridge.py` |
| блок «Демоны» в окне | `src/renderer/src/tabs/SettingsTab.tsx` |

Правила:

- **демон — отдельный процесс**; лечащий, сетевой сторож и сторож сессий не
  смешиваются (разные кулдауны и правила);
- **второй экземпляр не поднимаем**: перед стартом проверяем живой процесс;
  демон опознаётся по командной строке **без аргументов** (разовые вызовы
  `--send`/`--list` — не демон);
- **демон переживает окно**: процессы отсоединённые, закрытие программы их не
  убивает;
- **страховка без программы**: демон, чей файл изменился, поднимает себя сам
  (`minigen_core.respawn_self`);
- **пауза перед подъёмом** — иначе программа подняла бы вторую копию демона,
  который поднимает себя сам (урок 22.11: две копии лечащего брали аккаунты
  у КАРМАНА дважды);
- **надзиратель — ровно один** (`bridge/minigen_lock.py`): следить за демонами
  претендуют и фоновая копия, и окно (мост окна — отдельный процесс), но
  надзор получает владелец **системной блокировки файла** (`msvcrt.locking`
  на Windows, `flock` на POSIX). Блокировку снимает ОС, когда процесс
  умирает, — в отличие от файла-флага, который протухает и оставляет демонов
  без присмотра. Кто надзирает — видно в «Настройки» → «Демоны»;
- **API занимается эксклюзивно**: на Windows `HTTPServer` по умолчанию ставит
  `SO_REUSEADDR`, и второй процесс **занимал тот же порт `:8097`** (проверено
  на машине) — вызовы сетевого сторожа делились между экземплярами. Теперь
  порт берётся с `SO_EXCLUSIVEADDRUSE`, а экземпляр, которому порт не
  достался, **выходит**, а не продолжает следить за демонами вторым.

## Самообновление (Ф5)

Нейросеть может править модули самой программы. Механика — в
`bridge/minigen_code.py`, набор инструментов — `code.*` в
`bridge/minigen_tools.py`.

```
владелец: «найди нестыковку и почини»
   │
   ├─ code.search / code.read        — понять код
   ├─ code.branch                    — отдельный worktree + ветка
   │                                   (agent/minigen-fix-<slug>)
   ├─ code.patch                     — точная замена (фрагмент ровно один раз)
   ├─ code.tests                     — проверки репозитория в том же worktree
   ├─ code.commit → code.pr          — ветка → PR → master (решение — человек)
   └─ code.discard                   — правка не нужна: убрать worktree и ветку
```

Почему так:

- **отдельный worktree**: «МиниГен» (область `p-minigen`) уже занят этой
  сессией; второй писатель в том же дереве ломал бы чужую работу;
- **PR, а не пуш в master**: канон репозитория; решение о слиянии — за
  владельцем;
- **секреты закрыты**: `config.yaml`, `.env*`, `auth.json`, `*.pem`, `*.key`
  и файлы с именами `token`/`secret`/`password` не читаются;
- **правка точная**: неоднозначная замена отклоняется — приблизительная
  правка это порча кода;
- **ядро не трогаем**: `minimax-*.py` — боевой код с выученными уроками,
  его правка остаётся за человеком.
