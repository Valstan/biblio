# RUNBOOK: что делать, когда сломалось

Симптом → причина → действие. Порядок — от дешёвого к дорогому: сначала
посмотреть, потом дёрнуть, потом чинить.

## МиниГен (эта программа)

### Окно открылось, но все вкладки пустые, в шапке «мост не запущен»

**Причина:** не нашёлся Python или не поднялся `bridge/minigen_bridge.py`.

**Действие:**

1. Проверить Python: `python --version`.
2. Проверить мост вручную из папки программы:
   `python bridge\minigen_bridge.py` — должен молча ждать ввод (это нормально).
3. Если Python стоит не в `PATH` — указать путь явно:
   `set MINIGEN_PYTHON=C:\...\python.exe`.
4. Посмотреть stderr моста: в окне он виден в шапке (кратко) и в
   `%LOCALAPPDATA%\minigen-gui\` (журнал программы).

### «конфиг не читается!» в шапке

**Причина:** `mcode-project-areas.json` занят записью (панель пишет его
переключателем «Автомат/Вручную»). Раньше это приводило к падению демонов.

**Действие:** подождать секунду — мост читает конфиг с повтором. Если не
прошло — открыть файл и проверить JSON:

```powershell
python -c "import json;json.load(open(r'C:\Users\valstan\bin\mcode-project-areas.json',encoding='utf-8'))"
```

Если файл побит — восстановить из копии рядом (`mcode-project-areas.json.bak-mode`).

⚠️ **Копии конфига в репозитории нет** (канон владельца 27.11): список областей —
локальная вещь компьютера, в GitHub ему не место (на другом компьютере должны быть
свои локальные области). Восстановление — только локальное: из копии рядом или
вручную (через панель «МиниГен» область заводится заново).

### Чат: «нейросеть недоступна»

**Причина (по порядку):** протух токен области → нет сети/прокси → отказ по
очкам `50110` → нет ключа в `config.yaml`.

**Действие:**

1. Проверить сеть: вкладка «Сеть» → «Проверить все».
2. Проверить вход области: вкладка «Области» → колонка «Вход».
3. Если токен протух — лечащий обновит его сам; можно форсировать:
   вкладка «Области» → «Новый вход» у области `minigen`.
4. Если модель всё недоступна — **это не поломка программы**: сторожа
   продолжают работать, чат просто не отвечает.

### Кнопка «Перезапуск» ничего не делает

**Причина:** скрипт остановки не убил главный процесс десктопа.

**Действие:** кнопка сама это проверяет и добивает дерево процессов. Если
окно осталось — закрыть его руками; следующий «Старт» поднимет новое.

### Вкладка «Области» не показывает область

**Причина:** у области нет каталога данных (`~/.minimax-areas/p-<slug>`) либо
она не запущена.

**Действие:** вкладка «Настройки» → «Пути» — проверить `Каталоги областей`.
Если каталога нет, область надо создать заново («Создать область») или
восстановить каталог из копии.

## Сторожа (если окно их не показывает)

Сторожа живут **отдельно** от окна: их поднимает и водит программа «МиниГен»
в фоновом режиме (`bridge/minigen_bridge.py --daemon`, автозапуск Windows).
Окно только наблюдает и показывает; состояние видно в «Настройки» → «Демоны».

| Демон | Состояние | Один разовый проход |
|---|---|---|
| лечащий | `python C:\Users\valstan\bin\minimax-autheal.py --status` | `--once` |
| сетевой | `python C:\Users\valstan\bin\minimax-netwatch.py --status` | `--once` / `--recover` |
| сторож сессий | `python C:\Users\valstan\bin\minimax-sessionwatch.py --status` | `--list` |

### Отказ по очкам (`50110`) в области

**Причина:** у области кончились очки.

**Действие:** лечащий берёт следующий аккаунт у КАРМАНА сам (если область в
режиме «Автомат»). Если область в режиме «Вручную» — владелец меняет вход
кнопкой «Новый вход». Проверить: `python ...\minimax-autheal.py --status`.

### «Connection error» / «fetch failed» во всех областях

**Причина (важно!):** чаще всего это **мёртвый порт прокси**, а не аккаунт.

**Действие:**

1. Проверить порт прокси (панель сети → «через что идёт сайт»).
2. Сетевой сторож чинит это сам (каскад: Happ → смена сервера → резерв →
   рестарт ядра).
3. **Не** брать новый аккаунт: сначала путь, потом аккаунт. Это правило
   владельца, зафиксировано в журнале 21.11.

### Область «потеряла вход»

**Причина:** стор сгорел после ротации, либо протух токен.

**Действие:** «Новый вход» у области (или ждать лечащего). Если аккаунт
не наш — лечащий не будет жечь пул: это «нужен вход владельца», и в окне
это видно в колонке «Вход».

### Сессия «скомпактилась» / «контекст заполнен»

**Причина:** рантайм сжал контекст — дальше сессия «тупеет».

**Действие:** ротация (сторож делает сам). Вручную — «ротация» в чате или
через `python ...\minimax-sessionwatch.py --rotate <область> <сессия>`.

### Модель «нестабильна» (вендор)

**Причина:** вендор отвечает 5xx / перегрузкой.

**Действие:** **не перезапускать десктоп** — это убивает живые сессии
(23.11, «Матрица РМЗ 2»). Сторож ждёт восстановления вендора и продолжает
сессию сам.

## Пул генов: обмен наработками между копиями

Копии «МиниГена» обмениваются наработками через отдельный репозиторий GitHub:

```
Valstan/minigen-genepool      ← пул (приватный, ветка `pool`)
%LOCALAPPDATA%\minigen-gui\genepool   ← его клон на машине
```

Ген лежит в `genes/<копия>/<ген>/` и состоит из `manifest.json`, `patch.diff`
и `notes.md`. Формат и правила — в README пула.

Внедрение идёт **только через ветку + проверки + PR**: `genes.adopt` создаёт
ветку в своём клоне, применяет ген, гоняет проверки и открывает PR в
репозиторий программы. Решение — за владельцем.

Родословная: принятый ген записывается в `%LOCALAPPDATA%\minigen-gui\
lineage.jsonl` (копия) и в `lineage/<копия>.jsonl` пула (общая картина).

Внутри программы — вкладка «Управляющий», инструменты `genes.list`,
`genes.read`, `genes.publish`, `genes.adopt`.

## Свой клон копии на GitHub

Каждая копия «МиниГена» работает в своём репозитории GitHub и своём рабочем
дереве:

```
%LOCALAPPDATA%\Programs\МиниГен\clone   ← рабочее дерево копии (рядом с программой)
%LOCALAPPDATA%\minigen-gui\genepool     ← клон пула наработок между копиями
```

Репозитории: `origin` — свой (например `Valstan/minigen-<идентификатор>`),
`upstream` — репозиторий программы (`Valstan/biblio`). Правки идут в ветку и
пушатся в `origin`, PR открывается в `upstream`.

⚠️ GitHub **не даёт** завести форк своего же репозитория в своём же
аккаунте («A single user account cannot own both a parent and fork»), поэтому
копия заводит свой репозиторий с `upstream` на репозиторий программы — рабочий
процесс тот же (ветка у себя, PR — в upstream).

⚠️ И PR из такого репозитория GitHub **не открывает** («Head sha can't be
blank … Head ref must be a branch» — ветку он ищет только среди форков сети).
Живой случай 24.11. Поэтому `code.pr` отправляет ветку **ещё и** в репозиторий
программы — под именем `agent/<идентификатор копии>/<слаг>` (идентификатор
копии, чтобы две копии с одинаковым названием правки не столкнулись), и PR
открывается оттуда. Канон при этом цел: ветка → коммит → push → PR → зелёный
гейт → слияние; прямой пуш в `master` невозможен (хук машины).

⚠️ Прямой пуш в `master` на этой машине запрещён глобальным хуком
(ADR-0002, постулат 17) — **любого** репозитория. Поэтому код программы в
репозитории копии лежит в ветке `base`, а `master` в репозитории копии не
заводится.

Внутри программы — вкладка «Управляющий», инструменты `clone.status`,
`clone.setup`, `clone.sync`.

## Вторая копия на другом компьютере

**Короткий ответ на вопрос владельца: да, второй компьютер — это и есть схема
«A → B».** Настоящий обмен между копиями требует двух разных машин (или хотя
бы двух разных профилей `%LOCALAPPDATA%`): пути программы зашиты в коде, и
две копии на одной машине делят настройки, родословную и пул генов — см.
«Две копии на одной машине» в конце раздела.

### Что нужно на второй машине

| что | зачем | без него |
|---|---|---|
| Node.js 18+ | сборка окна (`npm install`, `npm run build`) | окно не соберётся |
| Python 3.10+ | мост программы: состояние областей, сторожа | окно откроется, но без состояния областей |
| `git` | клон программы и правки в своём репозитории | править программу нечем |
| `gh` с правами на аккаунт | **только** для режима «свой репозиторий на GitHub» | в режиме «папка в общем репозитории» (по умолчанию) не нужен |

### Режим копии: что выбрать на второй машине

При первом запуске копия спрашивает владельца, как ей работать (заказ
владельца 25.11, промты #130 и #131). Три режима:

| режим | что делает | аккаунт на GitHub | PR в программу | обмен наработками |
|---|---|---|---|---|
| **«папка в общем репозитории»** (по умолчанию) | копия правит программу в ветке `copies/<идентификатор копии>` того же репозитория | не нужен | открывается | есть |
| **«свой репозиторий на GitHub»** | копия заводит свой репозиторий `minigen-<идентификатор копии>`, ветки живут в нём | нужен, `gh` с правами | открывается | есть |
| **«только локально, без сети»** | правки идут в локальный git-репозиторий на машине | не нужен | **не открывается** | **недоступен** |

Сменить режим можно в окне (Настройки → режим копии). Отказ от регистрации
папки = режим «только локально»: программа при этом работает как обычно.

### Откуда взять

Готового установочного пакета программа не собирает: `install.ps1` ставит
зависимости и собирает окно **из исходников**. Поэтому нужен клон репозитория
программы (или архив релиза с этой папкой):

```
git clone https://github.com/Valstan/biblio
cd biblio\tools\minigen-gui
```

### Как запустить установку

Двойной клик по `tools\minigen-gui\Запустить.cmd` — он сам вызовет
`install.ps1` (если нет `node_modules\electron\dist\electron.exe`), соберёт
окно, если нет `out\main\index.js`, и запустит окно. То же самое вручную:

```powershell
powershell -ExecutionPolicy Bypass -File tools\minigen-gui\install.ps1
```

Установщик идемпотентен: ставит программу в `%LOCALAPPDATA%\Programs\МиниГен`,
делает ярлык «МиниГен» на рабочем столе и автозапуск «МиниГен (демоны)»; путь
исходников пишет в `%LOCALAPPDATA%\minigen-gui\settings.json` как `codeRepo`
— только если ключа ещё нет (установка поверх ничего не затирает).

### Своя копия на GitHub

⚠️ Свой репозиторий на GitHub заводит **только** режим «свой репозиторий на
GitHub». В режиме по умолчанию («папка в общем репозитории») копия работает
веткой `copies/<идентификатор копии>` в репозитории программы — и аккаунт на
GitHub не нужен вовсе.

В чате программы (вкладка «Управляющий»):

- `clone.setup` — завести свою копию в текущем режиме: клон рядом с
  программой, `upstream` на репозиторий программы, клон пула наработок, а в
  режиме «свой репозиторий» — ещё и сам репозиторий копии. Опасное действие
  (создаёт репозитории в вашем GitHub-аккаунте) — только с подтверждением;
- `clone.status` — проверить: репозиторий копии, `upstream`, ветка, за какой
  веткой в репозитории копия следит, отстал ли `master` от программы, есть ли
  незакоммиченные правки;
- `clone.sync` — обновить клон и пул (только fast-forward; локальные правки
  не трогаются: если дерево грязное — шаг пропускается).

То же самое из командной строки на машине, где есть `gh` с правами на
аккаунт: модуль `bridge/minigen_clone.py`, функция `setup()`.

### Имя репозитория копии заранее не угадать

Имя — `minigen-<идентификатор копии>`, а идентификатор (`mg-` + 8 случайных
символов) **случаен и у каждой копии свой**: он рождается на машине при первом
обращении и пишется в `%LOCALAPPDATA%\minigen-gui\instance.json`. Поэтому:

- своё имя искать не надо — оно видно в `clone.status` и `lineage.show`;
- у двух копий имена не совпадут, коллизий не будет;
- наружу (в пул наработок) уходят только идентификатор копии и хеши
  коммитов — ни имён машин, ни путей (D-038).

### Обмен «A → B»

Общий пул наработок — репозиторий `Valstan/minigen-genepool` (на каждой
машине его клон: `%LOCALAPPDATA%\minigen-gui\genepool`, ветка `pool`).

1. Копия A публикует наработку — `genes.publish` (уходит в пул, видят другие).
2. Копия B читает пул — `genes.list`, `genes.read` — и внедряет ген:
   `genes.adopt` создаёт ветку в своём клоне, применяет ген, гоняет проверки и
   открывает PR в репозиторий программы.
3. Слияние — за владельцем.

### Две копии на одной машине — только с раздельными профилями

Пути зашиты в коде: `%LOCALAPPDATA%\minigen-gui` (настройки, родословная,
пул генов) и `%LOCALAPPDATA%\Programs\МиниГен` (программа и её клон). Вторая
копия на той же машине получит свой `instance_id` и своё имя репозитория, но
перезапишет `instance.json` и `settings.json` первой и будет писать в тот же
клон и тот же пул генов. Если две копии на одной машине всё же нужны — нужны
**раздельные профили** (свой `%LOCALAPPDATA%` на каждую копию).

### Ключи и доступы

Свои и вне git (D-038): учётные данные GitHub для `gh`, ключи программы — в
её файлах. Репозиторий программы и его `master` не трогаем: правки копии идут
из своего клона, PR — в `upstream`.

### Проверено вживую (25.11 и 26.11)

Живой случай: копия на этой машине (`mg-693f8fdd`) — репозиторий копии
`Valstan/minigen-693f8fdd` (приватный, ветка `base` — код программы) на
месте, клон рядом с программой чистый, `upstream` — репозиторий программы,
клон пула на месте на ветке `pool`. Режим копии — «папка в общем
репозитории»: папка `copies/mg-693f8fdd` зарегистрирована в репозитории
программы (ветка `copies/mg-693f8fdd`).

Живая проверка 26.11 (промт #98) нашла два дефекта механики обновления —
оба исправлены (`bridge/minigen_clone.py`):

1. **`clone.sync` падал на исправной машине.** Он тянул текущую ветку клона,
   а у ветки копии `copies/<идентификатор>` не было слежения ⇒ git отвечал
   «There is no tracking information for the current branch», и владелец видел
   «обновление не прошло». Теперь регистрация папки заводит слежение, а
   обновление идёт от master программы.
2. **Папка копии переставала обновляться.** Регистрация пересоздавала ветку
   копии от master программы, а push шёл без force ⇒ как только master
   программы уезжал вперёд, push отвергался как non-fast-forward («папка не
   ушла в репозиторий программы»). Теперь master программы **вливается** в
   ветку копии: история дополняется, а не переписывается, — push проходит без
   force. Заодно локальный `master` копии догоняет программу (правки копии
   берутся из него), и если master программы переписан — не трогаем, а
   говорим прямо (правило «только fast-forward»).

Оба дефекта закрыты регрессионными тестами на настоящем git
(`bridge/tests/test_clone_lifecycle.py`).

**Живой прогон исправленного обновления на этой машине (26.11):** `clone.sync`
— `ok=True`; пул генов — «Already up to date»; `master` копии догнал программу;
ветка копии ушла в репозиторий программы fast-forward'ом (без force), и у неё
появилось слежение (`upstream/copies/mg-693f8fdd`). Иными словами: обновление
копии на живой машине работает.

⚠️ Сама **установленная** программа на этой машине ещё со старым мостом —
чтобы окно работало с исправлением, программу надо обновить (раскатка либо
«Обновить программу» в окне). Это релиз: делается по слову владельца.

## Локальная база «МиниГена»: перенос на другой компьютер (промт #92)

База лежит на машине: `%LOCALAPPDATA%\minigen-gui\minigen.db` (рядом с
`settings.json`). Данные переносятся **одним файлом** — выгрузкой.

1. **На старой машине:** «Настройки» → карточка «База «МиниГена»» → кнопка
   **«Выгрузить базу»**. Файл выбирается в диалоге (по умолчанию —
   `minigen-<дата>-<время>.minigen.json`). Файл с данными уходит с машины
   только по решению человека.
   То же из чата: «выгрузи базу» — нейросеть зовёт `db.export`, тоже через
   подтверждение; без пути файл кладётся в
   `%LOCALAPPDATA%\minigen-gui\exports\`.
2. **Перенесите файл** на флешке. Это обычный JSON — его можно и открыть
   глазами.
3. **На новой машине:** «Настройки» → «База «МиниГена»» → **«Импортировать
   базу»**. Программа сначала **разбирает** файл и показывает план: что
   перенесётся, что совпадёт с вашей базой, что конфликтует и какие виды
   данных она не знает. В этот момент **ничего не меняется**.
4. **Спорные записи решаете вы:** «взять из файла», «оставить своё» или
   «положить рядом отдельной записью». Без решения запись остаётся нетронутой —
   молчаливых перезаписей нет.
5. **«Импортировать»** — и отчёт: что перенесено, что осталось неразобранным,
   что перезаписано по вашему решению.

> **Перед импортом сделайте выгрузку своей базы** — это ваша точка отката
> (как вернуть базу назад — в таблице ниже).

### Если что-то пошло не так

| Симптом | Что делать |
|---|---|
| В базе лежит «неразобранное» | Это чужие или будущие виды данных. Они **не потеряны**: программа их не знает, но сохранила целиком и увозит в следующей выгрузке. Когда она их заучит — разложит по местам. |
| Импорт не пошёл, база не тронута | Так и должно быть: конфликты без решения не трогаются. Разберите файл ещё раз и решите спорные записи. |
| База не открылась | Скопируйте `%LOCALAPPDATA%\minigen-gui\minigen.db` в сторону и удалите — программа создаст новую пустую базу. Старый `prompts.db` остаётся запасной копией. |
| Нужно откатить импорт | **Надёжный откат — файл базы.** Скопируйте `%LOCALAPPDATA%\minigen-gui\minigen.db` (со всеми `-wal`/`-shm`) в сторону **до** импорта и верните его на место, если что-то пошло не так. Если копии нет — залейте выгрузку, сделанную **до** импорта, обратно, но по конфликтам выбирайте **«взять из файла»**: именно это возвращает прежние значения («оставить своё» оставит текущие, то есть ничего не откатит). ⚠️ Импорт ничего не удаляет — записи, которых не было в той выгрузке, останутся; полный откат = вернуть файл базы. |

### Отдельно про старую базу промтов

`%LOCALAPPDATA%\minigen-gui\prompts.db` — база хранилища промтов **старой**
версии программы (там таблица на каждую сущность — привязка к версии).
Программа переносит её в универсальную базу **при каждом старте** (но только то,
чего в новой базе ещё нет — перенос безопасный и повторяемый), и старый файл
**не трогает** — он остаётся запасной копией. Если перенос не прошёл, промты
всё равно видны в окне: хранилище читает старый файл.

## Первый запуск копии: вопрос и режимы

При первом запуске копия спрашивает владельца: **регистрировать ли свою папку
в репозитории программы**. Вопрос показывается один раз; ответ сохраняется в
родословной копии (`instance.json`) и в настройках.

Где смотреть и отвечать: **окно «МиниГен» → «Настройки» → карточка «Копия
«МиниГена»»**. Там же — переключатель режима и честная строка про обмен
наработками.

### Три режима

| Режим | Что делает | Обмен с копиями |
|---|---|---|
| **Свой репозиторий на GitHub** | копия заводит свой репозиторий, ветки и PR — в общий репозиторий программы | доступен (пул генов) |
| **Папка в общем репозитории** (дефолт после согласия) | правки и PR идут прямо в общий репозиторий программы | доступен (пул генов) |
| **Только локально, без сети** | правки идут в локальный git-репозиторий на машине (история, откат, diff) | **недоступен** |

### Отказ не ломает программу

Если владелец отказался, копия работает в локальном режиме: чат, области,
демоны и правки программы на месте. Менять режим можно в любой момент в
«Настройках».

### Что честно говорит локальный режим

- **PR не открывается** — GitHub недоступен; правка остаётся в ветке, её видно
  в diff'е (`code.pr` так и отвечает: «локальный режим: PR не открывается»);
- **пул наработок не обновляется** — `clone.sync` отвечает «обновлять нечего»;
- **обмен с другими копиями недоступен** — единственный путь вручную:
  «Выгрузить папку» (`genes.export`) → отнести соседней копии → «Внести
  папку» (`genes.import`).

### Подсказки наработок

Вкладка «Гены» показывает чужие наработки с **причиной** совпадения: те же
файлы, что копия правит сейчас, или та же часть программы. Чужая наработка
попадает в программу **только через ветку и PR** — «Внедрить» спрашивает
подтверждение, а решение остаётся за владельцем.

## Токен копии: как выдать и как принять

Токен подтверждает право копии работать **со своей папкой** в общем репозитории
программы (`copies/<идентификатор копии>/`). GitHub-кредом он не является:
GitHub не умеет ограничивать токен путём внутри репозитория, поэтому токен —
это подтверждение личности копии и привязки к её папке.

Где смотреть: **окно «МиниГен» → «Настройки»** — карточка **«GitHub»** (состояние
токена, поле для кода) и карточка **«Заявки на токен»** (заявки копий).

### Порядок действий

1. **Копия просит.** Кнопка «Запросить токен» → заявка уходит в раздел КАРМАНА
   `MiniGen-tokens`: родословная копии и подпись. Секрета в заявке нет.
2. **Владелец выпускает.** В его «МиниГене» карточка «Заявки на токен» →
   «Выпустить токен». Значение показывают **один раз**, отдельной карточкой
   «Выпущенный токен» (по умолчанию под маской, кнопка «Показать»).
3. **Передача.** Владелец отдаёт копии **код целиком** (`секрет.доказательство`,
   одной строкой). Через общий раздел секреты не ходят — раздел читают все, у
   кого есть канал, поэтому код передают вручную (мессенджер, другой канал).
   В чат «МиниГена» код не вставляют: переписка сохраняется на диске.
4. **Копия принимает.** Поле «Токен, который дал владелец» → «Сохранить токен».
   Копия пересчитывает доказательство **против своей родословной**: если код
   чужой — токен даже не ляжет в стор, доступ закрыт.
5. **Проверка.** Кнопка «Проверить доступ» — честный ответ: есть доступ или нет.

### Что означают сообщения

| Сообщение | Что это значит | Что делать |
|---|---|---|
| «токена нет» | токен ещё не получен | «Запросить токен» и дождаться кода от владельца |
| «токен не подтверждён под свою папку» | код выдан другой копии (или доказательство повреждено) | запросить код заново; проверить, что вставлен **весь** код, а не только секрет |
| «токен сохранён, но без доказательства» | вставлен только секрет | вставить код целиком (`секрет.доказательство`) |
| «доступ закрыт» при проверке чужой папки | так и должно быть | ничего: токен на чужую папку не действует |

### Где лежит токен

Вне репозитория, в сторе на машине: `%LOCALAPPDATA%\minigen-gui\credentials\`:

- `copy-token.txt` — значение секрета (в программе видна только маска);
- `copy-token-meta.json` — метаданные: чья папка, отпечаток, доказательство;
- `issued\<идентификатор копии>.json` — записи о выпущенных токенах (секрета
  там нет).

В журнал, в отчёты и в переписку значение токена **не попадает** (D-038):
мост пишет только «команда: ок», наружу отдаются путь, отпечаток и маска.

⚠️ Честная граница: токен **не даёт** копии прямого write в общий репозиторий
программы. Правки копии попадают в программу через посредника — пул наработок
и программа владельца открывают PR.

## Нейросеть предложила правку программы (вкладка «Управляющий»)

Значит, встроенная нейросеть нашла нестыковку в коде «МиниГена» и хочет её
починить. Так и должно работать: она читает код, правит его **в отдельном
worktree** и оформляет PR. Дальше — решение человека.

**Что посмотреть в первую очередь:**

1. **PR** — ссылка появляется в чате рядом с вызовом `code.pr`.
2. **Diff** — что именно поменяно. Правка применяется только если фрагмент
   встречался ровно один раз: это защита от «приблизительных» замен.
3. **Проверки** — `code.tests` гоняет тесты моста, приёмку панели и приёмку
   записи конфига в том же worktree. Красные проверки ⇒ PR не открывать.

**Красные флаги (правку не принимать):**

- правится боевое ядро (`tools/minimax-project-areas/minimax-*.py`) — там
  выученные уроки, такие правки — за человеком;
- в правке читаются ключи или авторизация (инструмент их не отдаёт — значит,
  правка сделана вручную мимо инструментов);
- PR идёт не из ветки `agent/minigen-fix-*`;
- просит раскатку на боевую машину — раскатка **только по слову владельца**,
  отдельным действием.

**Отказаться от правки:** в чате — «убери эту правку» (модель вызовет
`code.discard`: worktree и ветка удаляются). Следить за оставшимися
worktree'ами:

```powershell
git -C D:\valstan\REPO\biblio-minigen worktree list
git -C D:\valstan\REPO\biblio-minigen branch --list "agent/minigen-fix/*"
```

**Правка не применилась («фрагмент не найден» или «неоднозначна»)** — это
хорошо: значит, модель искала неточно. Попросите её сузить поиск (`code.search`)
и повторить.

**Правка уехала не туда:** файлы берутся из worktree, а не из дерева сессии,
поэтому дерево сессии (`D:\valstan\REPO\biblio-minigen`) не затронуто. Если
видится мусор в дереве — проверьте `git status` в worktree, а не в основном.

## Мигают окна консоли (PowerShell/терминал появляются и тут же исчезают)

**Симптом.** На экране то и дело появляются окна терминала или PowerShell и
сразу закрываются. Слышно жалобу владельца: «окна постоянно появляются и
закрываются тут же».

**Причина (проверено на машине, 23.11).** Демоны запущены **отсоединённо** —
консоли у них нет вовсе (`GetConsoleWindow()` = 0 при любых флагах). А вот их
дочерние консольные процессы (`powershell`, `cmd`) без флага
`CREATE_NO_WINDOW` получают **свою** консоль — то самое окно. Отдельно:
`CREATE_NO_WINDOW` действует только на консольные приложения и **игнорируется**
рядом с `DETACHED_PROCESS` — поэтому флаг нужен на *дочерних* запусках, а не
на запуске самого демона.

Главный источник был в сетевом стороже: проверка «слушает ли порт» жила в
PowerShell (`Get-NetTCPConnection`) и вызывалась **десятки раз за проход**
(проход идёт каждые ~190 с) — отсюда и пачки окон, и «слишком много запросов».

**Как проверить, что окна не появляются.** Запустить в фоне счётчик
процессов и посмотреть, кто и что поднимает:

```powershell
Register-WmiEvent -Query "SELECT * FROM Win32_ProcessStartTrace" -SourceIdentifier ProcStart
# ... подождать минуту, затем:
Get-Event -SourceIdentifier ProcStart | Group-Object SourceEventArgs |
  Select-Object Count, Name
```

Должно быть пусто (ну, кроме ваших собственных команд).

**Что сделано (PR #87).**

- проверка порта переписана на чистые сокеты (`socket.create_connection`):
  ни одного процесса, миллисекунды вместо ~0,5 с, и ответ тот же;
- `CREATE_NO_WINDOW` добавлен **каждому** дочернему консольному запуску в
  демонах (сетевой сторож, переключатель, лечащий);
- регрессионный тест `tools/minimax-project-areas/test_no_console_windows.py`
  (в CI) запрещает любой запуск процесса без `creationflags` и проверяет,
  что проверка порта не порождает процессов.

**Если окна всё же мигают** — значит, на машине старые файлы демонов: они
приезжают **раскаткой** (эталон — `master`):

```powershell
python D:\valstan\REPO\biblio-minigen\tools\minimax-project-areas\minigen_rollout.py
```

## Чат «Управляющий»: переписка, техблоки, отчёты

### Где лежит переписка

`%LOCALAPPDATA%\minigen-gui\chat-history.json` — **на машине, вне репозитория**
(D-038: в переписке бывают имена хостов, пути и ответы инструментов). Файл
ведёт **мост**, окно его только читает и рисует.

- предел: **200 реплик или 1 МБ** — что наступит первым; старые уходят первыми;
- формат: `{"version": 1, "updated_at": …, "messages": [{"role", "text",
  "calls", "attachments", "at"}]}` (вложения — файлы, приложенные оператором,
  промт #90);
- кнопка «Очистить» в чате чистит и файл, и память агента.

### Переписка пропала после перезапуска окна

1. Проверь файл: `%LOCALAPPDATA%\minigen-gui\chat-history.json` — есть ли он и
   не пуст ли.
2. Проверь, что мост отвечает: команда `chat.history` (окно → мост). Пустой ответ
   при живом файле = мост читает не тот файл (проверь `%LOCALAPPDATA%` у процесса).
3. Окно восстанавливает переписку **один раз — при пустом состоянии**. Если
   владелец ушёл на другую вкладку и вернулся, переписка на месте: состояние
   живёт в общем месте окна (`tabs/chat-store.ts`), а не в компоненте вкладки.

### «В чате появились отчёты сторожей»

Так и должно быть: перед ходом нейросети подкладывается сводка непрочитанных
отчётов. Но в **историю** отчёты не попадают — они подсказка хода, а не реплики.
Если отчёт виден отдельной репликой в переписке — это дефект: сводка должна
уходить в системную подсказку хода (`Agent.ask(..., note=…)`).

### В ответе сырой JSON

Не должен быть виден: главное в реплике — текст модели, а вызовы инструментов
свёрнуты («Что сделано: N действий») и раскрываются по клику. Подробности
(полные аргументы и полный результат) — внутри свёртки, без обрезки. Если JSON
выводится сразу, без свёртки — это старый бандл: пересобери и перезапусти окно.

### Проба самоотладки (Управляющий чинит программу сам)

Отчёт о пробе — `tools/minigen-gui/docs/SELFDEBUG-REPORT.md`. Цепочка, которую
должна пройти проба: `code.search → code.read → code.branch → code.patch →
code.tests → code.commit → code.pr` (последние три — опасные, ждут
подтверждения владельца).

### Файлы в чате: кнопка и перетаскивание (заказ владельца 24.11, #90)

**Как приложить файл:** кнопкой «Прикрепить файл» рядом со строкой ввода или
перетаскиванием **в любое место окна чата**. Файл показывается «чипом» над
строкой ввода; «×» на чипе снимает вложение. Отправка — обычной кнопкой
«Отправить» (можно отправить файл и без текста).

**Что уходит в модель:** текст и документы — текстом, картинки — картинкой
(модель их видит). ⚠️ **Файл уходит в вендор** — подпись об этом есть в зоне
приёма.

**Читаются:** txt, md, csv, tsv, json, xml, ini, log и прочий текст (в том
числе в cp1251), png/jpg/jpeg/gif/bmp/webp, xlsx/xlsm, docx/docm, pptx/pptm,
odt/ods/odp, pdf, rtf, а также старые doc/xls (Word и Excel 97-2003) — «как
получится». Вид файла определяется по **содержимому**: картинка, переименованная
в `.txt`, придёт в модель картинкой, а текст без расширения (`README`) — текстом.

**Честные отказы (это не дефект):**

| Сообщение | Что делать |
|---|---|
| «файл больше 20 МБ» | приложить нужную часть или сжать |
| «картинка больше 10 МБ» | уменьшить картинку (вендор такие не принимает) |
| «в архиве больше 50 МБ данных» | файл-«бомба» (раздувается в сотни раз): приложить нужную часть |
| «поток PDF раздувается больше 50 МБ» | то же — приложить страницы по отдельности |
| «чтение заняло больше 20 секунд» | файл слишком сложный: приложить часть или другой формат |
| «формат не поддерживается» | сохранить в txt/xlsx/docx/pdf |
| «старый формат Word (.doc) не разобрался — сохраните в .docx» | пересохранить в `.docx` |
| «текст из PDF не извлёкся» | это скан или шрифт с нестандартной кодировкой: приложить текст или картинку страницы |
| «путь файла получить не удалось» | перетаскивание не сработало — приложить кнопкой |
| «этот файл оператор не прикладывал» | так нейросеть отвечает, когда её просят прочитать чужой файл: прикладывайте файл к чату |

⚠️ Если файл не прочитан, сообщение содержит его **полный путь** — видно,
какой именно файл оператор имеет в виду.

**Ничего не пишется:** файлы только читаются; рядом с ними не появляется ни
временных копий, ни чего-либо ещё. Проверено тестом: каталог файла после чата
не меняется.

**Что делать, если вложение не появилось в переписке:** перезапустите окно
(вкладка «Обновление» → «Перезапуск») — после раскатки программы открытое
окно продолжает работать на старом бандле.

## Обновление программы

Программа стоит в `%LOCALAPPDATA%\Programs\МиниГен`, исходники — в
репозитории. После `git pull` (или мержа PR) обновление делает раскатка:

```powershell
python D:\valstan\REPO\biblio-minigen\tools\minimax-project-areas\minigen_rollout.py
```

Она обновит и демонов в `C:\Users\valstan\bin`, и саму программу, и ярлыки.
Только демонов — с флагом `--no-program`.

⚠️ **Раскатка сама пересобирает окно** (правило от 27.11). Скрипт ставит бандл
окна из `out/` рабочего дерева, а демонов — из `master`. Если окно собрано из
кода **старее** раскатываемого, раскатка:

1. сама пересобирает окно (`npm run build` в `tools/minigen-gui`) — это минута-две;
2. а пересобрать не из чего (в дереве нет нужного кода / есть незакоммиченные
   правки / нет `node_modules`) — **останавливается и говорит прямо**, машину
   при этом не трогает.

Живой случай, который это закрывает: в master залили правки, окно не
пересобрали — раскатка прошла «успешно», а окно осталось на старой сборке
(метка `0d6094f` при master `f8d07b3`). Владелец видел «свежую» программу, а
новой кнопки в окне не было; перезапуск окна не помогал — перезапускался тот
же старый бандл.

⚠️ **Не запускать программу из рабочего дерева репозитория**: её версия
зависит от того, какая ветка checkout. Установленная копия от этого
не зависит — в этом весь смысл её отдельного места.

### Из окна: вкладка «Обновление»

Заказ владельца (24.11): обновление должно запускаться из графического
интерфейса и быть наглядным. Теперь так и есть — вкладка «Обновление»:

1. **«Проверить обновления»** — сходит в репозиторий и скажет, есть ли новая
   версия и сколько коммитов новых;
2. **«Обновить программу»** — забирает изменения, собирает окно
   (`npm run build`), ставит программу на место и перезапускает демонов;
   каждый шаг виден в журнале вкладки;
3. **«Перезапустить программу»** — появляется, когда на диске уже новая
   версия, а окно ещё старое.

⚠️ **Обновление — это сборка из репозитория, а не деплой.** Порядок тот же,
что и при ручной раскатке: `git pull` → сборка окна → раскатка. Никакого
«волшебного» сервера, который сам всё делает. Сборку окна раскатка умеет и
сама: если окно собрано из кода старее раскатываемого — пересобирает его
(иначе окно осталось бы старым, а «версия на месте» говорила бы про новый
master).

⚠️ **Окно работает на том коде, с которого стартовало.** Раскатка меняет
файлы на диске, но запущенный процесс продолжит работу на старом бандле.
Поэтому метка сборки (коммит, вшитый в окно при сборке) сравнивается с
установленной версией (`version.json`): разошлись ⇒ окно старше файлов ⇒
нужен перезапуск. Живой случай 24.11: окно, открытое до раскатки, работало
на старом коде, и при закрытии даже падало (уже исправлено, PR #95).

Если обновление остановилось с «в исходниках есть незакоммиченные правки» —
это защита: чужая работа не затирается. Разберись с правками и повтори.
Проверяются только **отслеживаемые** файлы: новые (незакоммиченные) файлы
обновление не трогает и останавливать его не должны (живой случай 25.11, PR #144).

## Демоны упали или не поднимаются

Программа сама поднимает упавшего демона (раз в минуту, с паузой 20 с). Если
демон не поднялся:

1. Проверить окно: «Настройки» → «Демоны» — видно, кто жив;
2. Проверить, жив ли фоновый режим программы:

```powershell
Get-CimInstance Win32_Process -Filter "Name='pythonw.exe'" |
  Where-Object { $_.CommandLine -match 'minigen_bridge.py --daemon' } |
  ForEach-Object { $_.ProcessId }
```

3. Если фонового режима нет — запустить ярлык «МиниГен (демоны)» из папки
   «Автозапуск» или вручную:
   `pythonw bridge\minigen_bridge.py --daemon`;
4. Поднять конкретного демона вручную можно из окна: «Настройки» → «Демоны»
   → «Запустить».

Демон, чей файл изменился (после раскатки), поднимает себя сам — если
супервизора нет, это делает он.

## Сброс сессии на месте (не «новая сессия»)

⚠️ С 26.11 (промт #172) сброс на месте — **ручной** инструмент: автоматический
путь лечения сессии решает **«Управляющий»** (см. следующий раздел), и сессия
**без отчёта о выполнении** больше не получает команду «заверши работу».

Заказ владельца (24.11): **не начинать новую сессию**, а в этой же — правильно
завершить, очистить и начать заново. Делает это сторож сессий сам, когда
контекст близок к пределу или рантайм только что сжал его.

Порядок (в стороже сессий, `reset_session`):

1. **правильно завершить** — сессия получает команду: записать состояние
   нитки в handoff-файл и напечатать итоговую сводку, затем остановиться
   (нить не теряется);
2. **очистить** — опускается порог компактизации рантайма
   (`contextManagement.compactionTriggerAt` в `config.yaml` области) и рантайм
   **сам сжимает контекст внутри этой сессии**;
3. **начать заново** — та же сессия продолжается командой «продолжи нитку»;
   новая сессия не открывается.

Ротация (архивирование + новая сессия) осталась **откатом**: если сброс не
удался — делаем как раньше. И есть кулдаун (2 ч): после сброса пик
заполнения остаётся высоким, и без паузы сторож гонял бы цикл.

**Вручную:** в окне — кнопка в сессиях; из командной строки —
`minimax-sessionwatch.py --reset <область> <session_id>`; из чата МиниГена —
инструмент `sessions.reset` (действие опасное, требует подтверждения).

⚠️ Правка порога компактизации — **текстом**: в `config.yaml` есть YAML-якоря,
пересборка файла их бы развернула.

## Лечение застрявшей нитки: решает «Управляющий» (промт #172)

Когда сессия застревает (контекст близок к сжатию, ход упал, отчёта о выполнении
нет), сторож сессий **не требует от неё завершения**. Решение принимает
**встроенная нейросеть программы** — та же, что отвечает в чате.

Как это устроено:

1. сторож собирает **факты** о ситуации (вердикт, есть ли отчёт о выполнении,
   событие сжатия контекста, заполнение, последний ход, **текст последнего
   сообщения сессии целиком**, репозиторий/ветка/worktree нитки, что осталось,
   критерии приёмки, открытые PR, параллельные сессии того же репозитория);
2. спрашивает программу: `POST http://127.0.0.1:8097/treat-decision`
   (`bridge/minigen_api.py`, токен как у всех маршрутов) — сервер живёт в том
   же процессе, что и встроенная модель; тело — конверт
   `{"facts": …, "area": …}` (ровно так же, как его шлёт демон);
3. получает **ровно одно** из трёх действий + текст инструкции обслуживаемому
   агенту + причину:

| действие | что делается |
|---|---|
| `продолжать` | сессию **не трогают**: не закрывают, не архивируют; если она стоит — мягко подтолкнуть («продолжи работу по нитке» — с тем, что делать) |
| `завершать` | закрыть можно: есть отчёт о выполнении либо так решил «Управляющий» |
| `новая_сессия` | перенос нитки: паспорт → корректно завершить старую → архивировать → открыть новую и отдать ей паспорт + «продолжи нитку» |

**Правило-фолбэк** (модель недоступна: нет очков, вендор лежит, программа не
запущена, ответ не по схеме): отчёт о выполнении есть ⇒ «завершать»; отчёта
нет ⇒ **«продолжать»**. Фолбэк **не требует завершать сессию без отчёта**.

⚠️ **Закрытая сессия** (работа закончена: ход завершён и есть финальный
ответ) переводится на `новая_сессия` при любом решении: «продолжать» на
месте неисполнимо (сессия закрыта), а «завершать» без переноса убило бы
нитку. Цепочка: паспорт → архив → **новая сессия с паспортом и «продолжи
нитку»**.

⚠️ **В закрытую сессию команда не уходит** (промт #184): перед отправкой
состояние сессии перечитывается, и в журнале видно
`сессия уже закрыта — команда не отправлялась`. Повтор той же команды при той
же ситуации — тоже невозможен (`та же команда уже отправлялась в эту сессию
— не отправлялась`); стражи стоят внутри `send_to_session()`, поэтому
работают и для карусели полос, и для панели.

**Паспорт нитки** — `%LOCALAPPDATA%\minigen-gui\thread-passports.json`
(на машине, **вне репозитория**, D-038): что делалось, что осталось,
репозиторий, ветка, worktree, открытые PR, критерии приёмки, файлы нитки и
пометка «чужие деревья не трогать» (ADR-0011: один пишущий агент — одно
дерево; при пересечении — ждать merge и ребейзить). Файл переживает перезапуск
окна. Посмотреть паспорт: `minimax-sessionwatch.py --passport <область>
<session_id>`.

Решение видно в журнале и в «ящике отчётов» («ящик отчётов» → вид «session»):
**кто решил** (Управляющий / правило-фолбэк) и **кто исполнил** (сторож
сессий), какое действие, почему, что сделано.

⚠️ Решение лечения **тратит очки аккаунта**: спрашивается только когда вердикт
требует действия, и не чаще одного раза в 2 ч на сессию — **но** если
ситуация изменилась (другой вердикт, другой ход, сессия закрылась), решение
принимается заново.

## Модель нейросети: выбор в окне и применение к областям

Вкладка **«Управляющий»** → блок над перепиской: **модель**, **размер контекста**,
**уровень эффорта**. Кнопки:

- **«Сохранить»** — выбор применяется к собственному чату МиниГена и к его
  действиям в областях (раньтам уходит `--model`/`--effort`);
- **«Применить к областям»** — те же настройки становятся **родными
  дефолтами** каждой рабочей области: `defaultModel`,
  `defaultModelContextWindow`, `defaultModelThinking.effort`,
  `defaultModelVariant` в её `config.yaml`.

**Списки — не выдуманные.** МиниГен читает их из родного конфига провайдера
области (`config.yaml`), то есть из того же источника, что и рантайм:

| что в конфиге | что показывает окно |
|---|---|
| `models.<id>.contextWindowOptions` | допустимые размеры контекста |
| `models.<id>.contextWindowOptionHints` | подсказки (например `higher_usage`) |
| `models.<id>.thinking.effortOptions` | уровни эффорта (`default`…`max`) |
| `models.<id>.variants` | варианты мышления (thinking on/off) |
| `models.<id>.limit.output` | максимум ответа |

Поэтому список останется верным, когда появится другая платформа: МиниГен
подхватит её модели и её параметры сам.

**Что выбрано по умолчанию (23.11):** `MiniMax-M3.1-Flash`, контекст
**1 000 000**, эффорт **max** — как просил владелец. Это родные дефолты
области; выбор оператора их перекрывает, а значение, которого платформа не
объявляет, **отбрасывается** (иначе рантайм его отвергнет: «context_limit
must be supported by the selected model»).

⚠️ Проверено пробой вендора: `thinking: {type: "enabled", effort: "max"}`
принимается (200 OK), `max_tokens` — до 128 000 (родовой лимит модели).

## Как понять, что «МиниГен» жив и какой версии

**В шапке окна** (видно на любой вкладке):

- **демоны N/3** — сколько сторожей живо: лечащий, сетевой сторож, сторож
  сессий. Зелёный чип — все трои;
- **надзиратель: это окно** / **надзиратель: фоновый режим** / **надзирателя
  нет** — кто сейчас следит за демонами. Надзиратель должен быть **один**
  (иначе демоны поднимаются дважды);
- в подписи под названием — **версия** (коммит) и **установленная копия** либо
  **рабочее дерево** (это запуск из репозитория, разработка — в бою так быть
  не должно).

Та же строка «Надзиратель» есть в «Настройках» → «Демоны», рядом с кнопками
перезапуска.

**Когда окно закрыто** — три способа посмотреть из PowerShell:

```powershell
# 1. демоны живы?
Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
  Where-Object { $_.CommandLine -match 'minimax-(autheal|netwatch|sessionwatch)' } |
  ForEach-Object { "$($_.ProcessId) $($_.CommandLine)" }

# 2. фоновый режим (надзиратель) жив?
Get-CimInstance Win32_Process -Filter "Name='pythonw.exe'" |
  Where-Object { $_.CommandLine -match 'minigen_bridge' } |
  ForEach-Object { "$($_.ProcessId) $($_.CommandLine)" }

# 3. журнал: демоны пишут туда каждый проход
Get-Content "$env:LOCALAPPDATA\mcode-web\journal.log" -Tail 20
```

**Старая веб-панель** (`:8099`) и её супервизор (`:8098`) **архивированы и не
запущены** с 23.11 (Ф6): демонов держит программа «МиниГен». Если порт
`:8099` отвечает — значит, архив кто-то поднял руками.

## Два надзирателя демонов (демоны перезапускаются дважды)

**Симптом.** В журнале подряд идут «ДЕМОНЫ: лечащий не жил — поднял (pid …)»
две или три раза за пару минут, а демон при этом живой. Или: окно открыто, и
демоны «умирают» сами по себе.

**Причина.** Надзирать за демонами могут **двое**: фоновая копия программы и
окно (мост окна — тоже отдельный процесс). Второй поднимает демона в тот же
момент, что и первый, — и демоны перезапускаются по кругу. На Windows к этому
добавляется перехват порта `:8097` (`SO_REUSEADDR` разрешает двум процессам
слушать один порт): обращение сетевого сторожа («перезапусти контур») может
уйти не к тому экземпляру.

**Как увидеть.** Кто надзирает — видно в «Настройки» → «Демоны» (строка
«Надзиратель») и в файле `%LOCALAPPDATA%\minigen-gui\supervisor.json`:

```powershell
Get-Content "$env:LOCALAPPDATA\minigen-gui\supervisor.json"
Get-CimInstance Win32_Process -Filter "Name='pythonw.exe'" |
  Where-Object { $_.CommandLine -match 'minigen_bridge.py --daemon' } |
  ForEach-Object { "$($_.ProcessId)  $($_.CommandLine)" }
```

**Что делать.**

1. Лишние копии — из дерева репозитория (`D:\valstan\REPO\...`), а не из
   `%LOCALAPPDATA%\Programs\МиниГен`: их надо остановить
   (`Stop-Process -Id <pid> -Force`) — программа живёт в своём месте, из
   репозитория её запускать нельзя.
2. Раскатка делает это сама: `minigen_rollout.py` останавливает устаревших
   менеджеров и поднимает фоновый режим из установленного места.
3. После 23.11 (PR #86) надзиратель защищён системной блокировкой: её
   получает один процесс, второй выходит. Следить за демонами вручную не
   нужно — второй надзиратель просто не появится.
