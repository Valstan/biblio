# MiniMax Code: изолированный экземпляр на каждый проект

Утилиты владельца для PC79: **свой экземпляр MiniMax Code на каждый проект** — своя
рабочая папка, свои сессии, свой ярлык на рабочем столе, и **в панели задач видно имя
проекта**, а не «MiniMax Code» у всех окон.

## Что внутри

| Файл | Что делает |
|---|---|
| `mcode-project-areas.json` | **список областей**: slug, название для панели задач, папка проекта, раздел КАРМАНА. Живёт в `C:\Users\valstan\bin\`; копия здесь — **в git и в раскатке** (27.11: файл не был в списке раскатки ⇒ репозиторий и машина расходились молча — четыре области, заведённые на машине, в git не попадали) |
| `mcode-project-start.ps1 -Project <slug>` | запуск изолированного экземпляра проекта: свои каталоги данных, своя папка, свой AUMID, переименование окна |
| `mcode-project-title.ps1 -TargetPid N -Title "..."` | фоновый теггер: держит заголовок окна «<Проект> — MiniMax Code» (приложение само его перебивает) |
| `mcode-project-stop.ps1 [-Project <slug>]` | остановить экземпляр проекта или все (основной десктоп не трогает) |
| `make-mcode-project-shortcuts.ps1` | пересоздать ярлыки рабочего стола; старые ярлыки областей убирает в папку «MiniMax — старые ярлыки» |

Живут в `C:\Users\valstan\bin\` (рядом с прочими лаунчерами MiniMax). Копия здесь — в git.

### Кто главный: репозиторий или машина

**И то, и другое — по своим полям** (27.11, после того как расхождение всплыло):

- **репозиторий** — эталон **структуры**: какие области есть, их названия, папки,
  разделы КАРМАНА. Раскатка везёт эту часть на машину;
- **машина** — эталон **живого состояния**: `autoheal` («Автомат / Вручную») и
  `driver` (водитель проекта) переключает владелец в панели «МиниГен» ⇒ раскатка
  их **сохраняет**, а не откатывает молча;
- область, заведённая **на машине** и ещё не перенесённая в git, не удаляется —
  раскатка говорит о ней в отчёте («только на машине»), и её надо перенести в
  репозиторий руками (или автоматической правкой через PR — отдельная задача).

Формат файла задаёт **программа** (`minigen_state.write_projects` → `indent=2`):
копия в git должна быть **побайтно** такой же, иначе каждая раскатка переписывала
бы файл на машине в чужом формате, а программа — обратно.

## Как это устроено

**Изоляция — оба параметра сразу** (иначе изоляции нет):

- `--user-data-dir=<каталог>\electron` — снимает single-instance lock;
- `MINIMAX_DATA_DIR` / `MAVIS_DATA_DIR` — свои auth, сессии, настройки, лимиты.

Каталог данных проекта: `C:\Users\valstan\.minimax-areas\p-<slug>`. Авторизация
копируется из уже авторизованной области (`area1`), иначе на каждый проект нужен
отдельный вход (device-flow, по одному за раз).

**Различимость в панели задач — два независимых рычага:**

- `--app-user-model-id=MiniMaxCode.<slug>` — свой AUMID, окна не группируются;
- переименование окна Win32 `SetWindowText` — метка в панели задач.

Заголовок ставит **фоновый теггер**, а не однократная установка: приложение
переустанавливает «MiniMax Code» сам, и метка без теггера живёт недолго.

## Второй экземпляр ТОГО ЖЕ проекта

Когда нужна вторая параллельная сессия по тому же проекту — заводится **вторая
область**: свой slug в `mcode-project-areas.json`, свой каталог данных, свой AUMID,
свой заголовок окна, свой ярлык, своя строка в панели и **свой аккаунт** (refresh
одноразовый — общий с первой областью невозможен).

**Рабочая папка — `git worktree`, а не то же репо.** Канон проекта запрещает двух
пишущих агентов в одном рабочем дереве. Worktree — не копия репозитория, а вторая
рабочая папка **того же** репо: общие `.git`, история, ветки и remote, поэтому
«синхронизация через GitHub» работает сама (fetch приносит коммиты в оба дерева,
push идёт в тот же репозиторий обычным PR-flow).

```powershell
# 1. worktree с веткой под вторую сессию
git -C D:\valstan\REPO\MatricaRMZ worktree add `
    D:\valstan\REPO\MatricaRMZ\.claude\worktrees\m2 -b agent/matricarmz-2 main

# 2. зависимости в worktree (свой node_modules)
cd D:\valstan\REPO\MatricaRMZ\.claude\worktrees\m2
corepack pnpm install --frozen-lockfile

# 3. область в конфиг, затем ярлыки
#    { "slug": "matricarmz2", "title": "Матрица РМЗ 2", "folder": "<worktree>" }
powershell -ExecutionPolicy Bypass -File C:\Users\valstan\bin\make-mcode-project-shortcuts.ps1

# 4. запуск
powershell -ExecutionPolicy Bypass -File C:\Users\valstan\bin\mcode-project-start.ps1 -Project matricarmz2
```

**Правила второй сессии:** один агент — одна задача — своя ветка (в первом экземпляре
ветку не переключают); зависимости ставятся в worktree отдельно; **стенд не дублировать**
— backend-api на `PORT=3001`, Postgres на 5432, трекер на 6969, два одновременных
`pnpm dev` бьются по портам (во второй сессии гоняют гейты: typecheck / lint / test).

**Аккаунт области** ставится через панель («Новый вход (токен)») или напрямую:

```powershell
python C:\Users\valstan\bin\minimax-switch.py pull p-matricarmz2 --apply
```

## Авто-лечение областей (`minimax-autheal.py`)

Демон живёт **под присмотром программы «МиниГен»** (мост в режиме `--daemon`,
автозапуск при входе в Windows): поднимается, если не жил, и следят за ним
же. Цикл (раз в 3 мин): обнаружить отказ по очкам
→ взять аккаунт у КАРМАНА → **активировать бонус** (`POST /signin/claim`) →
перезапустить область → отправить **«Продолжай»** в её сессию.

**Признак отказа — вендорский код, а не текст в переписке:**

| Уровень | Что смотрим | Когда лечим |
|---|---|---|
| T1 | в строке сессии `local_runtime_sessions`: `error_code = 50110` («insufficient balance (1008)») | отказ после установки текущего аккаунта **и** область после отказа не двигалась |
| T2 | ход упал, не дав ни одного ответа агента | только после живой проверки (`mcode exec` → провайдер ответил отказом по очкам) |
| T3 | в сторе области нет записи входа или приложение считает себя вышедшим | лечится так же, **но только если аккаунт у области уже был** (иначе это «нужен вход владельца» — пул не жжём) |

Токен проверяется **до установки**: остаток жизни access ≥ 30 минут **и**
вендор отвечает 200. Не прошёл — берём следующий аккаунт (до трёх попыток).

Границы: кулдаун 30 минут на область; нет аккаунта у КАРМАНА — ждём; основной
десктоп (без `--user-data-dir`) не трогаем никогда.

Состояние — по областям:

```powershell
python C:\Users\valstan\bin\minimax-autheal.py --status
```

Разовое лечение по команде: `python C:\Users\valstan\bin\safe_heal.py <область>`.

**«Продолжай» встаёт в начало, а не в очередь:** если в сессии идёт ход, CLI
отказывается («Session already has an active Turn»). Тогда лечащий срывает
зависший ход перезапуском области и отправляет «Продолжай» заново.

## Watchdog очков (`minimax-points.py`)

Реактивное лечение ловит отказ провайдера **после** того, как он случился
(`error_code = 50110`): ход к этому моменту уже упал. Watchdog даёт два
**опережающих** сигнала.

### 1. Остаток очков — по данным сайта MiniMax (главный сигнал)

**Остаток очков виден на сайте, и читается тем же токеном, что и модель.**
Эндпоинты — те самые, что дёргает веб-консоль MiniMax:

| запрос | что отдаёт |
|---|---|
| `GET /minimax-cloud/api/v1/credit/details` | леджер дневных грантов: `granted_amount`, `remaining_amount`, `consumed_amount`, `granted_at_ms`, `expire_at_ms` |
| `POST /matrix/api/v1/commerce/get_membership_info` | одна цифра: `op_credit_summary.total_remaining_amount` |

⚠️ **Очки накапливаются.** Каждый дневной грант (400 или 1000) живёт **~29.8
суток** (`expire_at_ms − granted_at_ms`, проверено на всех грантах) и остатки
складываются. Тратится остаток по очереди, с самых старых грантов. Поэтому
«сегодняшняя клетка» из `signin/status` — это **не** остаток: у бывшего
аккаунта p-orca остаток 4779.70 при дневном гранте 400.

**Калибровка (замер на живом окне 26.11):** 1 очко ≈ **837 биллинговых токенов**
(`input + output`; кэш не тарифицируется — он в 30–240 раз больше при той же
ёмкости аккаунта).

**Порог по остатку.** Один запрос стоит медианой 1 178 токенов, но на хвосте
(p99 по 133 657 запросам) — 206 138 токенов ≈ **246 очков**, максимум — 845 тыс.
≈ 1 009 очков. «10 очков» из первого обсуждения — слишком туго: при 10 очках
аккаунт умирал бы прямо посреди хода.

**Порог выбрал владелец 27.11.2026 — 150 очков** (≈125 тыс. токенов запаса,
«подмены чаще»). Это перекрывает медиану запроса, но **уже не перекрывает хвост**:
при остатке 150–246 очков один крупный запрос может перечеркнуть остаток, и
провайдер откажет на середине хода. Владелец выбрал это осознанно (аккаунты в
пуле КАРМАНА кончаются, а живой ход важнее). Меняется на область:
`minimax-points.py set <область> <очки>`.

### 2. Учёт расхода по аккаунту (запасной сигнал)

База рантайма области (`v2/sqlite/runtime-state.sqlite`, таблица
`local_runtime_token_usage`) пишет по каждому запросу к модели
input/output/cache_read. Биллинговый расход = `input + output`.

Считается **по аккаунту, а не по сессии**: один аккаунт пула со временем стоит в
нескольких областях (101 аккаунт из 153 побывал больше чем в одной области), и
очки у него общие. Окно — от установки аккаунта, но не раньше суточного сброса
очков (03:00 MSK): вчерашний расход сегодняшними очками не оплачивается.

Этот сигнал работает, когда остаток узнать не удалось (сайт недоступен, токен
протух). Как основной он слабее: **номинал очков ёмкость аккаунта не задаёт**
(400 и 1000 очков умирают при одном расходе), а остаток видно прямо.

### 3. Проба аккаунта

Прямой запрос к модели (`POST {baseURL}/messages`, `max_tokens=1`, промпт «ping»)
токеном области. Ответ: жив / кончились очки / недействительный вход /
неясно (сеть). Сетевая ошибка — это **не** «кончились очки» (урок 21.11:
«fetch failed» = мёртвый порт прокси, аккаунт при этом цел). Если остаток виден
и равен нулю, ход к модели не делается вовсе — аккаунт отвергается сразу.

| Файл | Что делает |
|---|---|
| `minimax-points.py` | остаток очков с сайта, учёт расхода по аккаунту, пороги, проба, состояние |
| `minimax-autheal.py` | вердикт T4 «ПОЧТИ БЕЗ ОЧКОВ» + проба аккаунта при установке |

```powershell
python C:\Users\valstan\bin\minimax-points.py status           # остаток, расход, пороги
python C:\Users\valstan\bin\minimax-points.py balance          # остаток очков с сайта MiniMax
python C:\Users\valstan\bin\minimax-points.py probe p-minigen  # проба аккаунта
python C:\Users\valstan\bin\minimax-points.py learn            # выученная статистика отказов
python C:\Users\valstan\bin\minimax-points.py set p-minigen 150              # порог по очкам
python C:\Users\valstan\bin\minimax-points.py set-budget p-minigen 800000    # порог по расходу
```

**Простаивающие области не трогаются:** если к модели не обращались дольше 10
минут, расход не растёт и подменять аккаунт незачем.

### Токены: сколько их на самом деле

**Один.** В сторе области лежит ровно одна запись входа: `clientId =
mcode-public`, `audience = agent-backend`, `scopes = [agent.default]`, токен
непрозрачный (60 символов), срок 12 часов (Карман выдаёт на 720 минут). Он же
работает и к модели (`POST {baseURL}/messages`), и к облачному API сайта
(`/minimax-cloud/api/v1/*`, `/matrix/api/v1/*`) — отдельного «веб-токена» не
нужно.

Отдельные сроки у **очков**, а не у токенов: дневной грант живёт ~30 суток, и
очки разных дней складываются в общий остаток аккаунта. «40 дней» — не
второй токен, а срок жизни начисления (плюс длинная кука Akamai на сайте с
Max-Age 31536000).

Refresh-токен у кармановских аккаунтов — **заглушка** (`stub-…`): работает
access, продлить вход нельзя, по истечении берётся следующий аккаунт. У старых
областей (реальный вход через браузер) refresh настоящий — его можно обменять
на новый access, но это отдельная работа, и сейчас она не нужна.

## Сетевой сторож (`minimax-netwatch.py`) и сторож сессий (`minimax-sessionwatch.py`)

21.11.2026, по заказу владельца: «МиниГен» **сам** возвращает связь и оживляет
сессии. Три демона живут под супервизором, у каждого свои правила и кулдауны:

| Демон | Что чинит | Кулдаун |
|---|---|---|
| `minimax-autheal.py` | **АККАУНТЫ**: отказ провайдера `50110` | 30 мин на область |
| `minimax-netwatch.py` | **СЕТЬ**: прокси, VPN-сервер, доступ к модели | 10 мин на каскад |
| `minimax-sessionwatch.py` | **СЕССИИ**: работа стоит / упала по сети / забит контекст | 15 мин на «Продолжай» |

Общие куски (журнал, состояние, конфиг областей, чтение базы рантайма, запуск
`mcode`) — `minigen_core.py` (шим `minigen-core.py` — для старых ссылок).

  хотя аккаунт был цел ⇒ пул Кармана жечь нельзя.

**Правило:** если `mcode` падает с `fetch failed` — сначала проверь порт
прокси, а не аккаунт. Переменные лежат в `HKCU\Environment`; **процессы могут
держать старые значения** (унаследовали от момента запуска), даже когда в
реестре уже исправлено ⇒ сверять оба источника.

**Как чинит сетевой сторож:** берёт значения из реестра (или живой порт из
конфига) → пишет их в реестр и своё окружение → перезапускает контур
«МиниГена» (старый процесс новых переменных не наследует) → помечает время
восстановления, и сторож сессий поднимает упавшие по сети нитки.

```powershell
python C:\Users\valstan\bin\minimax-netwatch.py --status   # пути, вендор, прокси-переменные
python C:\Users\valstan\bin\minimax-netwatch.py --once     # один проход
python C:\Users\valstan\bin\minimax-netwatch.py --recover   # каскад восстановления сейчас
```

### Каскад восстановления сети (шаг принимается только после успешной пробы)

1. `happ://disconnect` → `happ://connect` — переподключение Happ (прав админа не нужно);
2. **смена сервера в Happ** — запись `lastServer*` в
   `HKCU\Software\Happ\OrganizationDefaults\Preferences` + переподключение
   (кандидаты — из локального `happ-servers.json`, в git не попадает);
3. уход на резервный туннель `11081` + перезапуск контура;
4. смена апстрима резерва между своими REALITY-серверами;
5. перезапуск ядра Happ, если порт не слушается.

«Доступ появился» ≠ одна удачная проба: устойчивость = несколько успешных
проб подряд **+** живая проба вендора **+** прокси-переменные не сломаны.

### Сторож сессий: что он делает

Читает базу рантайма области и разбирает сессии: `работает` / `готова` /
`брошена` / `упала по сети` / `ждёт владельца` / `контекст заполнен`.

- **«Продолжай»** — только брошенным ниткам и упавшим по сети после
  восстановления связи. Готовую работу **не продолжаем** (заказ владельца):
  признак готовности — последний ход завершён **и** напечатана итоговая
  сводка **и** нет оборванных субагентов.
- **Ротация при заполнении контекста ≥ 95 %** (окно MiniMax-M3.1 = 1 000 000;
  считается по последнему ходу `input+output+cache_read`): команда корректного
  закрытия → ожидание закрытия → архивирование (точечный UPDATE одной строки)
  → **новая сессия** с начальной командой (handoff + итоговая сводка).

CLI (им же пользуется «Управляющий»):

```powershell

python C:\Users\valstan\bin\minimax-sessionwatch.py --read <область> <session_id>
python C:\Users\valstan\bin\minimax-sessionwatch.py --send <область> <session_id> "текст"
python C:\Users\valstan\bin\minimax-sessionwatch.py --close <область> <session_id>

python C:\Users\valstan\bin\minimax-sessionwatch.py --rotate <область> <session_id>
```

## Сторож оборванных субагентов (`minimax-orphans.py`)

Субагенты обрываются, когда кончаются очки: работа ребёнка теряется, а
родитель об этом не знает. Детектор находит таких детей:

```powershell
python C:\Users\valstan\bin\minimax-orphans.py [область]
```

Выводит `БУДИТЬ` (работа оборвана — поднимать) и `готово` (закончил — не
трогаем).

**Состояние ребёнка определяется его последним ходом.** В базе рантайма
(`<область>\v2\sqlite\runtime-state.sqlite`): запись фоновой задачи
(`kind=subagent`, `status=failed|canceled|aborted`) + `metadata.childSessionId`
+ последний ход ребёнка в `local_runtime_turn_ingress` — `completed` ⇒ работа
закончена, `failed`/`aborted` ⇒ оборвана.

**CLI не умеет открывать сессии субагентов:** `mcode exec --session <child>` →
«Sub-agent Sessions are internal and cannot be opened». Будить ребёнка можно
**только** инструментом рантайма `task_append` по `task_id` — он поднимает
ребёнка **с его же контекстом** (проверено живым тестом).

Лечащий (`minimax-autheal.py`) делает это сам: после перезахода области
сообщение «Продолжай» содержит список оборванных детей, чтобы родитель
разбудил их через `task_append`. Тех, чью работу он уже сделал сам, будить не
нужно — решает агент по своему контексту.

## Грабли (см. также пул brain_matrica)

- **PowerShell 5.1 читает `.ps1` без BOM как ANSI** — кириллица в скрипте ломает
  парсер («Unexpected token»). Файлы здесь сохранены **с BOM**.
- **Параметр скрипта не может называться `$Pid`** — это автопеременная PowerShell
  только для чтения («Cannot overwrite variable Pid»).
- **`Start-Process` склеивает `ArgumentList` пробелом без кавычек** — аргумент с
  пробелами разваливается, и фоновый скрипт падает **тихо**.
- **Ярлык и конфиг разъезжаются:** у старых областей `id` не совпадал с проектом,
  и ярлык «МОЗГ» открывал biblio. Источник правды — один json; ярлыки пересоздаются из него.
- **В обработчиках `onclick` нельзя оставлять `\'`**: панель — это JS-шаблонная
  строка, и `\\'` на выходе даёт `\'` в атрибуте ⇒ браузер получает невалидный JS,
  **весь inline-скрипт не парсится** ⇒ таблица пустая, кнопки «не работают». Сейчас
  обработчики без кавычек внутри атрибутов (`data-slug` + `this.dataset`).
- **PowerShell печатает в кодировке консоли (cp1251)** — панель читает UTF-8 ⇒
  «◆◆◆» в результатах. Вызов идёт через `[Console]::OutputEncoding=UTF8`.
- **Панель пишет конфиг сама** ⇒ рендер JSON зафиксирован в `renderConfig`; лишняя
  запятая в нём делала файл невалидным, и лечащий на минуту остался без областей.
- **Приёмка не должна брать настоящие ключи машины.** Каталог ключей ищется от
  `%USERPROFILE%` ⇒ без подмены домашнего каталога приёмка уходит в подставной
  сервис с **настоящим** токеном владельца (живой случай 26.11: токен чужого
  раздела попал в журнал запросов теста). Лечится подменой `HOME`/`USERPROFILE`
  на временный каталог.
- **Поле `karman` у области — это проект в КАРМАНе (учёт расхода MiniMax и
  комната vault'а), а не раздел библиотеки промтов.** У области `minigen` там
  «biblio» — раздел **дома утилит**: взять его как «свой» = забрать чужую
  работу. Раздел области — по её слагу (`minigen` → `MiniGen`), а `karman` —
  запасной путь для областей, у которых слаг на раздел не похож
  (`sabantuy` → `SabantuyMalmyzh`).
