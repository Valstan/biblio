## Обновление программы из окна + живой цикл гена (PR #106–#110)

### 1. Живой цикл гена — замкнут (PR #106, #109)

Заказ владельца (24.11): обмен наработками между копиями («пул генов»). Формат,
публикация, чтение и внедрение сделаны (PR #105), но **живой прогон не
замыкался** — и вскрыл три дефекта, все три — в инструментах, а не в задумке:

1. **патч гена был битый** (PR #106, `cc788f9`): diff брался в текстовом режиме,
   и `git apply` срезал финальный перевод строки ⇒ «corrupt patch». Теперь
   diff — байтами (`_git_bytes()` / `write_bytes`).
2. **приёмка панели указывала на несуществующий файл** (`minimax-project-areas/
   check_panel.py` вместо `archive/check_panel.py`) ⇒ «приёмка панели» всегда
   красная ⇒ правило «красные проверки — не PR» блокировало нейросети
   открывать PR вообще. Теперь отсутствие файла — понятная ошибка, а не
   красный шаг.
3. **`slugify` ронял кириллицу** (PR #107, `0282075`): название правки
   нейросеть пишет по-русски, а `[^a-zA-Z0-9]` выбрасывал кириллицу целиком ⇒
   **все** ветки назывались `agent/minigen-fix-fix`, все worktree'ы — `fix`, и
   вторая правка умирала с «worktree уже есть». Теперь транслитерация, хеш в
   крайнем случае и numbered-суффикс при повторе.
4. **GitHub не открывает PR из репозитория, который не форк** (PR #108,
   `da04ab7`): «Head sha can't be blank … Head ref must be a branch» — ветку он
   ищет только среди форков сети, а форк своего же репозитория в своём же
   аккаунте GitHub запрещает. Теперь `code.pr` проверяет через API, форк ли
   репозиторий копии, и если нет — отправляет ветку **ещё и** в репозиторий
   программы под именем `agent/<идентификатор копии>/<слаг>`, и PR открывается
   оттуда.

Живой итог: битый ген `gene-mg-693f8fdd-001` отозван из пула (коммит
`ccaa2c3`, запись об отзыве в летописи пула), ген `gene-mg-693f8fdd-002`
опубликован (`8326078`: патч 2201 байт, `git apply --check` — rc=0 **до**
публикации, манифест с верной базой `cc788f9`), внедрён через PR #109 (в PR
ровно один файл гена), слит (`1a27f5d`) и раскатан. Попутно закрыта мелочь из
прошлого handoff: раскатка убирает старые бандли окна (на машине было 7 файлов
в assets, 5 мёртвых — стало 2 живых).

Родословная копии `mg-693f8fdd`: поколение 2, родитель — ген
`gene-mg-693f8fdd-002` от `cc788f9`; летопись пула: published → published →
retracted → adopted.

**Честное ограничение:** обмен проверен на одной копии (опубликовала и внедрила
она же). Формат многокопийный (поле `author`, свой файл летописи на копию),
но настоящий обмен «копия A → копия B» требует второй копии, а значит ещё
одного репозитория в аккаунте владельца — это его решение.

### 2. Обновление программы из окна — наглядно (PR #110, `113f6db`)

Вопрос владельца (24.11): «как вобще у него обновление происходит… как мне
понять что он обновился до новой версии, и как мне запустить процесс
обновления из графического интерфейса программы? Сделай процесс обновления
наглядным».

**Ответ на «как это работает»:** никакого деплоя. Обновление — это **сборка
из репозитория**: `git pull` → `npm run build` (electron-vite) → раскатка
(`tools/minimax-project-areas/minigen_rollout.py`: копирование в своё место,
перезапуск демонов, `version.json` с коммитом и родословной) → перезапуск
окна. Раньше это был ручной шаг владельца одной командой.

**Сделано:**

- `bridge/minigen_update.py` — `status()` / `check()` / `start()`: шаги
  «исходники → забрать → собрать → раскатка → готово», построчный журнал
  (в окне и в `%LOCALAPPDATA%\minigen-gui\update.log`), **одна реализация
  раскатки** (тот же скрипт, что и вручную);
- **чужая работа не затирается**: незакоммиченные правки в исходниках ⇒
  обновление останавливается и говорит почему; нет `node_modules` — тоже;
- **честность версий**: при сборке в бандл вшивается коммит
  (`process.env.MINIGEN_COMMIT` в `electron.vite.config.ts`), окно сравнивает
  его с установленной версией (`version.json`) и, если разошлись, говорит:
  «на диске новее, чем в окне — перезапусти» + кнопка перезапуска
  (`app.relaunch()`). Живой случай 24.11: окно, открытое до раскатки, работало
  на старом коде — и при закрытии даже падало;
- вкладка «Обновление» в окне: установленная версия, метка сборки окна, что
  есть в репозитории, пошаговый журнал, кнопки «Проверить обновления» /
  «Обновить программу» / «Перезапустить программу»;
- инструменты нейросети `update.status` / `update.check` / `update.start`
  (последний — опасный, с подтверждением).

Живая проверка (из установленной программы): `update.status` → установлено
`113f6db`, в репозитории `113f6db`, позади 0; `update.check` → «программа
актуальна»; `update.start` → весь путь отработал (fetch → pull → build →
раскатка → «установлена версия 113f6db — перезапусти окно»).

Попутно исправлен тест, который **падал сам собой в 10:00**:
`bridge/tests/test_bridge.py` считал метки времени в подставном журнале от
«вчера 10:00», а окно статистики — «последние сутки». Теперь метки от
«сейчас», и тест не зависит от часов.

## Надзиратель и API — разные роли (PR #101, #102)

Живая находка 24.11 (07:31–08:00): после раскатки **порт `:8097` не
слушался** — локального API не было, демоны ж��ли (их поднимал лечащий), то
есть надзирателя не было вовсе, а раскатка рапортовала «готово».

Три причины, все — в том, что «зелёная проверка ≠ правильная правка»:

1. **раскатка врала**: она проверяла демонов, а не надзирателя ⇒ PR #101:
   `stop_managers()` ждёт ухода менеджеров, `start_installed_manager()` ждёт
   **ответа API**, и если надзирателя нет — раскатка не зелёная. Новая
   приёмка `test_rollout_keeps_supervisor.py` (в CI).
2. **роли были смешаны**: надзиратель демонов (блокировка `supervisor.lock`) и
   API (эксклюзивный порт) — разные вещи, но код требовал блокировку, чтобы
   поднять API. Открытое окно владельца держало блокировку ⇒ фоновый
   экземпляр выходил ⇒ API умирал вместе с ним ⇒ PR #102: блокировка нужна,
   чтобы **надзирать**, но не чтобы **слушать API**.
3. **проверка API не работала без токена** (CI это поймал): без файла токена
   запрос не делался вовсе ⇒ «API не отвечает» там, где он отвечал.

Живая проверка после правок: API отвечает (3/3 демона), надзиратель — окно
владельца (pid 26596), фоновый экземпляр держит API и честно пишет «надзор не
веду». Раскатка наконец говорит правду: «надзиратель: pid …, демонов N/3».

## Падение главного процесса при закрытии окна — исправлено (PR #95, `d21efe6`)

Жалоба владельца: при закрытии окна «МиниГена» выходит «A JavaScript error
occurred in the main process: Object has been destroyed at Bridge.event».

Причина (измерено, а не угадано): `mainWindow?.webContents.send(...)`
проверяет только `null`, но **не** проверяет, что окно уже уничтожено.
Закрытие окна ⇒ `window-all-closed` ⇒ `bridge.stop()` ⇒ дочерний Python-процесс
умирает и шлёт последнее событие («мост завершился») в уже мёртвое окно ⇒
главный процесс падает.

Сделано:

- `tools/minigen-gui/src/main/window-events.ts` — `sendToWindow()`: окно,
  `webContents` и сама отправка под защитой; гонка «окно умерло между
  проверкой и отправкой» не роняет процесс;
- `tools/minigen-gui/src/main/index.ts` — события моста идут через
  `sendToWindow()`, ссылка на окно обнуляется на `closed`, `show()` под тем же
  замком;
- регрессия `tools/minigen-gui/tests/window-events.test.ts` — 7 случаев
  (мёртвое окно, мёртвый `webContents`, гонка, отсутствие окна) + 2 проверки
  обвязки главного процесса, чтобы прямой `webContents.send(...)` не вернулся.

Проверено: `npm run typecheck`, `npm test` (11 тестов), `npm run build` —
зелёные; гейт CI зелёный; раскатано на PC79 (версия программы `d21efe6`).
Живая проба в настоящем Electron: старый вызов падает с «Object has been
destroyed» (поломка воспроизведена), новый — отправка пропущена, падения нет.

## Сброс сессии НА МЕСТЕ — вместо «начать новую сессию»

Заказ владельца (24.11): «может не начинать новую сессию, а просто тут же, в
этой сессии текущей, делать очистку/сброс сессии и начинать с начала? Чтобы
МиниГен умел это делать сам автоматически, если сессия приближается к лимиту
контекста или только что произошла компактизация».

**Что выяснилось в рантайме** (это и сделало заказ выполнимым):

- рантайм **сам сжимает контекст сессии** — и делает это **внутри сессии**;
  порог сжатия настраивается: `contextManagement.compactionTriggerAt` в
  `config.yaml` области (доля окна или абсолютное число токенов), по
  умолчанию ~95 %;
- компактизация **сохраняет идентичность сессии** — её id, историю и нитку;
- есть ACP-операции `session/fork`, `session/load`, `session/resume` — то
  есть продолжить **ту же** сессию штатными средствами ✓.

**Сделано (PR #94):**

1. `minigen_core.set_compaction_trigger(area_dir, fraction)` — порог
   сжатия ставится **нативно**, текстовой правкой `config.yaml` (в нём есть
   YAML-якоря — пересборка файла их бы развернула);
2. `minimax-sessionwatch.reset_session()` — **правильно завершить → очистить →
   начать заново в той же сессии**:
   - правильно завершить: команда «запиши handoff, напечатай итоговую сводку,
     остановись» (нить не теряется);
   - очистить: опустить порог компактизации — рантайм сожмёт контекст сам,
     внутри этой же сессии;
   - начать заново: та же сессия продолжается командой «продолжи нитку»
     (`mcode exec --session <id>`);

## Мигающие окна консоли — механизм доказан, а не угадан (PR #87)

Владелец пожаловался: «окна терминала или повершела постоянно появляются на

|---|---|---|
| `python.exe`, любые флаги (в т.ч. `DETACHED_PROCESS|CREATE_NO_WINDOW`) | 0 | **нет** |

процесса, 3 мс вместо ~0,5 с, ответ тот же); `CREATE_NO_WINDOW` добавлен
каждому дочернему консольному запуску; регрессионный тест

## Два надзирателя демонов: хвост Ф6 оказался не «процессом», а дырой

Продолжая нитку после вчерашней пятой части, первым делом проверил **живую
машину** — и нашёл, что хвост («старый фоновый экземпляр не удаётся
завершить») стоил дороже, чем казалось.

**Что было на машине:** жили **два** фоновых менеджера программы, оба из дерева
репозитория (`minigen_bridge.py --daemon`): pid 35472 (с 17:18) и pid 15420
(с 18:12). API `:8097` держал второй, а **надзирали за демонами оба** — и
демоны были перезапущены **дважды за две минуты** (19:52:42 и 19:54:47 в
журнале). Раньше это читалось как «демоны падают»; теперь видно, что их
перезапускали два надзирателя по очереди.

**Три дыры, из-за которых это возможно:**

1. **Надзирателей могло быть двое.** Проверка «жив ли другой экземпляр» по
   ответу API (PR #83) не закрывает гонку (два старта одновременно) и
   совсем не закрывает **окно**: мост окна — тоже отдельный процесс, и он
   тоже следит за демонами (`Bridge.start_daemon_supervision`).
2. **Порт API можно было перехватить.** `HTTPServer` в Python ставит
   `SO_REUSEADDR`, а на Windows с ним **второй процесс занимает тот же порт**
   — проверено на этой машине (`ApiServer` vs `ApiServer` на одном порту:
   второй поднялся). Значит, вызов сетевого сторожа «перезапусти контур» мог
   уйти не к тому экземпляру: у одного API без надзирателя, у другого —
   надзиратель без API. Ровно та половинчатая поломка, которую уже чинили
   в Ф6.
3. **Ошибка проглатывалась.** `daemon_mode()` ловил неудачный бинд API и
   **продолжал** работать — лишний экземпляр оставался надзирателем.

**Починено (PR #86):**

- **системная блокировка надзирателя** (`bridge/minigen_lock.py`):
  `msvcrt.locking` на Windows, `flock` на POSIX. Атомарна (гонки нет) и
  снимается ОС, когда процесс умирает, — в отличие от файла-флага, который
  протухает и оставляет демонов без присмотра. Надзор получает один
  процесс; остальные ждут (и подхватывают надзор, если владелец умер);
- **не смог поднять API — не надзиратель**: демон-режим выходит и отпускает
  блокировку;
- **порт — эксклюзивно**: `SO_EXCLUSIVEADDRUSE` на Windows;
- **раскатка** останавливает устаревших менеджеров (из дерева репозитория) и
  поднимает фоновый режим **из установленного места**;
- **окно показывает надзирателя** («Настройки» → «Демоны»: pid и путь) —
  дубль видно, а не угадывают;
- попутно убран протухший дубликат интерфейса `DaemonStatus` в `types.ts`:
  он сливался со вторым и ломал `typecheck`.

**Проверено:** гейт зелёный (`typecheck`, `npm test`, `npm run build`, тесты
моста — 58, из них 8 новых в `bridge/tests/test_lock.py`); **вживую**: новый

гейт записи блокирует завершение процессов (и это же — причина, по которой

2. владелец запускает раскатку — она останавливает их сама и поднимает

   `python D:\valstan\REPO\biblio-minigen\tools\minimax-project-areas\minigen_rollout.py`.

## Две поломки после архивирования панели — найдены и починены

Проверка живой машины после переключения (Ф6) нашла две вещи — обе тихие,
обе проявились бы позже и в другом месте.

**1. Перезапуск контура после смены прокси (критично).** Сетевой сторож
звал `http://127.0.0.1:8098/restart-contour` — страницу управления
архивированной панели. Вызов падал ⇒ каскад восстановления сети работал
**наполовину**: прокси переключался, а контур не перезапускался — лечащий и
сторож сессий оставались со **старыми** прокси-переменными и ходили по
мёртвому пути. Внешне это выглядело как «интернет плохой», а не как
сломанный механизм восстановления.

Починено (PR #77): перезапускает теперь **программа** — локальный API
`127.0.0.1:8097` с токеном (`GET /status`, `POST /restart-contour`,
`POST /restart?name=`). Сетевой сторож зовёт программу первой, старый
супервизор — запасным путём. Сетевого сторожа в контур не включают: он в
этот момент работает.

**2. Ярлык с остатком старого поля.** «МиниГен.lnk» на рабочем столе
сохранил аргумент старой панели (`http://127.0.0.1:8099/`): `WScript.Shell`
загружает существующий ярлык и оставляет поля, которые не заданы явно.
Установщик теперь чистит `Arguments` принудительно; мёртвый ярлык
«МиниГен — панель (управление)» перенесён в архив.

**Правило на будущее (общее):** когда у старого механизма есть «кнопка»,
которую зовут другие части системы, её нельзя убирать вместе с ним — сначала
найти **все** её вызовы (`8098`, `supervisor_alive`, `restart_contour`) и дать
новому владельцу тот же интерфейс. И при перезаписи ярлыка задавать ВСЕ поля
явно, иначе останется хвост от прошлой жизни.

**Ещё две мелочи, которые стоили похода по кругу (обе — про «тихую поломку»):**

1. **Метод запроса.** Старый супервизор отвечал на `/restart-contour` любым
   методом, а программа различает GET (чтение) и POST (действие). Сторож
   слал GET ⇒ уходил в 404, цепочка падала, а в журнал писалась **только
   последняя ошибка** (старый супервизор) — настоящая причина терялась.
   Теперь сторож шлёт POST, а программа принимает и GET тоже.
2. **Токен создавался только по запросу с токеном** — файл не появлялся
   никогда, и сторож не мог авторизоваться (замкнутый круг: позвать нечем,
   токена нет). Теперь токен создаётся **при старте** API.

**Живая проверка после починки:** вызов `restart_contour()` из боевого файла
сторожа → «СЕТЬ: контур перезапущен (http://127.0.0.1:8097/restart-contour)»;
лечащий и сторож сессий получили новые PID, сетевой сторож — нетронут (он в
этот момент работает), дублей нет.

**Хвост (не закрыт):** прежний фоновый экземпляр программы (`pythonw
minigen_bridge.py --daemon`, pid 35472) запущен ДО последних коммитов, и
завершить его не удалось — гейт записи блокирует завершение процессов. Он
безобиден (тот же «поднимать, только если не жив» ⇒ дублей не будет), а при
следующем входе в Windows умрёт сам: автозапуск поднимает только новый
экземпляр.

## ocvpn (2026-10-26)

Новая утилита `tools/ocvpn` (PR #26): локальный VPN-контроллер для OpenCode — sing-box
как ядро, ротация выхода по Clash API, сторож по логу OpenCode, дашборд на 18081.

- **Замер честный, но неутешительный**: 1500 нод из 12 публичных источников, по задержке
  живы 183; проба модели по **40** живым нодам (21 разная /24, 5 протоколов) — **0** дали
  квоту, контроль без прокси и через Happ отвечал и до, и после прогона. Публичный пул
  выжжен, годен только выход, которым больше никто не пользуется. Разбор —
  `brain_matrica/cross-project-ideas/gotchas/G501.md`.
- **Починено (PR #27)**: `fp=unsafe` (xray-значение) роняет sing-box — ядро отвергало
  13 нод из 1500 молча, на валидации конфига. Незнакомые отпечатки → `chrome`; пул шире
  (+8 источников, `node_limit` 1500), источники чередуются, `check_workers=60`
  (1500 нод проверяются ≈ за минуту). Плюс `server_password`: свой `opencode serve`
  требует пароль, без него проба через сервер падала с `Unauthorized`.
- **Черновики замеров** лежат в `tools/ocvpn/_tmp/` (каталог gitignored):
  `_probe_sources.py` ищет источники нод по GitHub, `_probe_fresh.py` гоняет пробу квоты
  по свежим нодам. Решение владельца: довести до команды утилиты или выбросить.

### Reality-линия в черновиках (разобрана 2026-10-26, позже PR #27)

После PR #27 в `_tmp/` накопился второй слой черновиков (`_reality_*.py`, `_sub_probe.py`,
`_probe_private.py`, `trace.json`) — там копалась одна аномалия: **наш собственный
reality-сервер не сходится с нашим ядром.** Симптом в `state/core.log`:
`open connection to api.ipify.org:443 using outbound/vless[...]: reality verification failed`,
то есть sing-box отвергает сервер и уходит в fallback; xray из установки Happ на тех же
параметрах соединяется и выход даёт.

- Проверены ядра **1.12.12** (ядро утилиты), **1.14.4** (stable) и **1.15.0-alpha.13** —
  отказ одинаковый во всех трёх, включая публичную reality-ноду `n116`. Стрелка «старое
  ядро» отпала.
- Матрица `flow: vision | без` × `fp: chrome | firefox` на той же ноде не лечила ничего —
  стрелка «параметры конфига навыворот» тоже отпала.
- **Reality как протокол при этом жив в sing-box**: в пуле 10 живых reality-нод прошли
  Clash-API delay, и их форма (`vision` + `chrome`/`firefox` + `short_id`) ровно та же, что
  у 300+ мёртвых. Значит отказ относится к конкретным серверам (наш и `n116`), а не к
  транспорту, и общий замер «живых 183 из 1500» этим дефектом не искажён.
- Практический вес: reality — 313 нод из 1500 (21 %), но в живых их 10. Обходного
  транспорта в утилите нет: не сошлось ядро — нода недоступна, хотя Happ её берёт.
- **Не закрыто:** даёт ли free-квоту приватный выход и 21 сервер общей подписки. Прогоны

  итерации — результата нет, и выдумывать его нельзя. Пул по-прежнему выжжен: 35 из 40
  кандидатов ответили `Free usage limit reached`, 4 обрыва, 1 таймаут.
- **Грабля**: `_sub_probe.py` и `_probe_private.py` в докстринге утверждают «xray сходится,
  sing-box нет», но лог этого утверждения не сохранился — только текст. Следующий замер по

## video-downloader: ffmpeg на склейке (2026-10-26)

Входящая директива Мозга `2026-10-09-video-downloader-ffmpeg-path` разобрана в
ту же сессию — **взяли** (PR #28). `download.py` отдавал в `ffmpeg_location`
**папку** `imageio_ffmpeg/binaries/`, а бинарь там `ffmpeg-win-x86_64-v7.1.exe`:
yt-dlp искал `ffmpeg.exe`, не находил и падал на склейке
(`merging of multiple formats but ffmpeg is not installed`). Теперь отдаём полный
путь (`imageio_ffmpeg.get_ffmpeg_exe()`), `_ffmpeg_dir()` → `_ffmpeg_exe()`.

- **Проверка без сети и без YouTube**: до фикса `FFmpegPostProcessor.available =
  False`, после — `True`; плюс настоящая склейка видео+аудио через
  `FFmpegMergerPP` с теми же `opts` (out.mp4, 12323 байта на этой машине).
- GUI не правился: он зовёт `download_urls()`, `opts` общие.
- Подтверждение Мозгу — `mailbox/to-brain/2026-10-26-video-downloader-ffmpeg-path-taken.md`.
  Неразобранных входящих в `from-brain/` больше нет.

**Инсайт**: `ffmpeg_location` у yt-dlp — это либо путь к **файлу**, либо каталог,
в котором лежит именно `ffmpeg.exe`. Отдать каталог с бинарём под другим именем —
значит сообщить yt-dlp «ffmpeg не установлен», причём молча и только на склейке:
скачивание одной дорожки при этом работает, поэтому дефект не виден до первого
`bv+ba`. Проверять такое надо не «видит ли yt-dlp ffmpeg», а настоящим
merge-проходом.

### net-monitor v1.1.0 (PR #12) — жалоба владельца на нестабильность

Симптом: правый клик по значку — меню долго не появляется, потом возникает в месте
клика, висит с курсором ожидания, пункты не реагируют, затем исчезает.

- **Причина найдена в устройстве, а не в интерфейсе**: весь цикл проверок шёл в потоке,
  который рисует меню — проверка канала Anthropic (таймаут до 10 с), страна выхода
  (до 3 запросов по 4 с), DNS- и TCP-пробы. Пока проба ждала, клик стоял в очереди.
  При исправной сети это незаметно: пробы отвечают за миллисекунды. Замирало ровно
  тогда, когда сеть плохая, — в единственный момент, ради которого утилита нужна.
- **Лечение**: отдельный фоновый runspace с очередью заданий (строго по одному —
  пробы и шаги восстановления не должны толкаться); поток интерфейса только забирает
  готовые результаты и рисует. Через ту же очередь идут шаги лестницы восстановления
  (`restart-vpn` ждёт поднятия туннеля до 20 с) и наполнение всех четырёх окон.
- Читающие функции и оба оконных отчёта переехали в `lib/probe.ps1` — фоновому
  исполнителю нужен один набор модулей. Текст модулей хранится строкой
  (`$script:LibSource`), поэтому одинаково работает и из папки `lib\`, и в склеенной
  однофайловой сборке; сборщик переписан под это и **проверяет склейку парсером**.
- **Версионирование**: единственный источник — `$AppVersion` в `net-monitor.ps1`.
  Видна первой строкой меню трея (наведение показывает папку запуска), в логе старта,
  в отчёте статуса и заголовке окна. Архив релиза — `net-monitor-<версия>.zip`.
- **Установка**: `install.ps1` + `Установить.cmd` ставят утилиту в
  `%LOCALAPPDATA%\Programs\net-monitor`, закрывают работающий экземпляр (любой версии
  и из любой папки), полностью замещают файлы, включают автозапуск, кладут ярлык в
  «Пуск» и запускают новую версию. Настройки и лог живут отдельно и переживают
  обновление. Повторный запуск установщика = обновление.
- **Правило против путаницы версий**: из репозитория утилиту не запускают — репозиторий
  для разработки, на машине живёт единственная установленная копия.

**Проверено:** парсер чист на всех пяти скриптах, BOM на `.ps1` на месте, `.cmd` —
ASCII; `-Once` и `-SelfTest` проходят; распакованная однофайловая сборка запускается;
установщик прогнан по-настоящему (закрыл dev-экземпляр, поставил v1.1.0, ключ

## Грабли и инсайты

- **Стоимость измерения максимальна в аварии.** Живой сервис отвечает за миллисекунды,
  мёртвый — по таймауту; разница на порядки. Поэтому «проверка быстрая, зову прямо
  здесь» — вывод, проверенный только на здоровой системе. Сбор показаний и их показ не
  должны делить ресурс, блокировка которого видна пользователю. Письмо Мозгу:
  [2026-08-27](../mailbox/to-brain/2026-08-27-the-probe-freezes-the-dashboard-it-reports-to.md).
- **Артефакт без видимой версии делает отчёты о себе непроверяемыми**: неизвестно, о
  какой сборке говорит баг-репорт. Версия — из самого артефакта, из одного места,
  в имени релиза. Там же, вторым разделом письма.
- **`.ps1` обязаны быть в UTF-8 с BOM** (запуск через `powershell` 5.1: без BOM файл
  читается как ANSI, кириллица ломается, скрипт молча перестаёт работать). `.cmd` —
  наоборот, ASCII без BOM. Проверять после каждого создания файла.
- Консольному установщику нужен явный `[Console]::OutputEncoding = UTF8`, иначе весь
  русский вывод — каша в OEM-кодировке.
